# OpenType macOS: current system state (as-built reference)

Status: descriptive, not a design doc. This is a snapshot of what the macOS
client actually does as of 2026-08-09, after a from-scratch rewrite (old
6-mode system deleted, then cut to exactly 3 modes, MLX-Whisper added for
local ASR, and the UI split Alfred-style into a menubar popover + a real app
window). It supersedes the mode/architecture *content* of earlier specs in
this directory for "what does the system do right now" purposes — those
specs (`2026-08-08-system-boundaries-and-memory-v1-design.md`,
`2026-08-09-b1-b2-mode-surface-design.md`,
`2026-08-09-b2-agent-runtime-v1-design.md`) are left as-is as a record of how
the design got here, and are still useful for *why* things are shaped this
way, but their mode lists (4-6 modes, Polish/Translate/X Reply, per-provider
tool-calling requirements) are stale. This doc is scoped to macOS because
**macOS is now the only platform in this repo**: iOS (`Platforms/iOS`),
Android (`Platforms/Android`), and the cross-platform contract
(`Shared/OpenTypeContract.json`, `Shared/Schemas/`) were removed outright
(product decision, not an oversight) rather than reconciled with the macOS
rewrite — don't go looking for them, and don't treat any older doc's
references to them (this directory's earlier dated specs, git history) as
describing current repo contents.

## 1. The 3 modes

`InputMode` (`Sources/OpenType/Models.swift`) has exactly three cases:

| Mode | Selection needed? | What happens | Sidecar call |
| --- | --- | --- | --- |
| `transcribe` | No | What MLX-Whisper hears is the result. **No LLM involved at all** — in any of its three delivery variants (§8): Direct delivers it verbatim, Tidy cleans it with deterministic local rules, Review stages it for the user to edit. | `/asr/transcribe` only |
| `ask` | No | Speaks a question; answered directly in the unified voice surface — the one bottom-center floating panel (`OverlayController`) that the listening HUD morphs into a result card (spec: `2026-08-13-hud-morph-result-surface-design.md`; the old center-screen `AskPanelController` popup is gone). The one mode that *answers* rather than preserves/transforms the input. If the Q&A tab has a conversation open (see §9), the question continues that thread instead of starting a fresh one-shot call. | `/asr/transcribe` then `/oneshot/ask` |
| `agent` | No | Speaks a task; dispatched non-blockingly to a tool-calling agent loop. Live step ticker + result card in the same unified voice surface as `ask` (dismissing it never cancels the run), plus the durable Agent tab record (§7/§9) and a completion notification. Same conversation-continuation behavior as `ask` if the Agent tab has a thread open. | `/asr/transcribe` then `/agent/run` |

Every mode's result is always copied to the clipboard (`OutputDeliveryPolicy.retainsClipboardCopy`, unconditionally `true`). Auto-insert into the currently-focused field is a separate, additional delivery step gated on the `automaticallyInsert` setting — never a replacement for the clipboard copy. Since 2026-08-15 a small built-in per-app table can withhold that step for named apps (terminals, where a pasted newline is a command the shell runs) and can supply a `TranscribeVariant` default for an app the user has never chosen one for; it only ever subtracts from what was asked for, and it is one switch away from being bypassed entirely — see §8's 按应用规则. No mode ever presses Return for the user: the spoken "发送 / press enter" command was removed outright (see §7), so `ContextBridge.insert(_:)` only ever pastes. `agent` in particular is draft-only, since a tool call inside the loop is itself an external action the instant it runs — this is a policy backstop, not a technical sandbox (see §6).

Mode switching is explicit — the mode-cycle chord, the menubar popover's `ModeGrid`, or a spoken mid-recording trigger ("agent 模式" / "agent mode" / etc., `VoiceModeRouter`) — never automatic classification of an ambiguous utterance.

**The mode-cycle chord (rewritten 2026-08-14, closing review items §6-7 and §6-9):** one rule — *hold the configured recording modifier, tap `Tab`*. Three defects made it effectively dead before, and all three are fixed:

- `AppModel.cycleMode()` opened with `guard state != .listening` — but holding the recording modifier is what *starts* a recording, so past the 300ms long-press threshold every cycle was rejected. `.listening` is now the gesture's main case, gated through `ModeCyclePolicy.allows` (only the mid-pipeline states `.transcribing`/`.transforming`/`.inserting`, plus `isBusy`/`isStartingRecording`, still refuse).
- Both the Tab gate and the old Shift half of the chord were hardcoded to left Option, so `fn` and double-tap users could never switch at all. The gate is now `GlobalHotKey.shouldCycleModeOnTab(heldModifierKeyCodes:preset:)`, which reads the active preset's own `modifierKeyCodes(for:)` set. The Space-chord presets register a Carbon hot key rather than the modifier-only event tap and so have no Tab handling — `usesModifierOnlyEventTap` is what says so, and `HotKeyPreset.modeSwitchHint` (the popover's hint copy, previously a hardcoded "点 Shift 或 Tab" string for every preset) is `nil` for exactly those.
- **The Shift half of the chord is removed outright** — Tab is the only mode-switch key now.

Cycling while `.listening` **retargets the in-flight recording**: `ModeCyclePolicy.cycle` moves `activeMode` as well as `configuration.selectedMode`, so the recording the user is still speaking into is processed as the new mode. (Retargeting mid-flight is not new — `VoiceModeRouter` already reassigns `activeMode` after transcription.) That path deliberately does *not* go through `selectMode(_:)`, whose `.modeChanged` toast would cover the live pill for 1.2s; it re-derives the surface instead, and since `voiceSurfaceMode` is `activeMode ?? surfaceRunMode ?? selectedMode`, the listening pill itself shows the new mode.

Tab **cancels nothing** (`GlobalHotKey.modeSwitchTabEffects`: `cancelsPendingLongPress` and `marksChordUsed` are both `false` — either one alone aborts the hold-to-talk the user is still holding for), so hold length rather than reaction time decides the outcome: release before the threshold and only the mode switched; keep holding and the recording proceeds as the new mode. Two things survive that removal: the `DoubleTapDetector` sequence is still reset at Tab time (a stale tap could otherwise fire an unrequested double-tap recording on the next tap), and a replacement flag `modeSwitchDidCycle` takes over `modifierChordWasUsed`'s other job of suppressing the release gesture — routed through the pure `GlobalHotKey.releaseGesture(longPressDidArm:modeSwitchDidCycle:chordWasUsed:)`, where an armed long press always wins. Tab is always swallowed, autorepeat included, so it never leaks into the focused app.

The chord branch sits **ahead of the stop-on-any-key branch** in `handleEventTap`, so while the recording modifier is held Tab means "switch mode", never "commit this recording". The converse is the one asymmetry worth knowing: during a *hands-free* (double-tap-started) recording the user's hand is off the modifier, so a bare Tab falls through to stop-on-any-key and commits. Cycling mid-recording there means pressing and holding the modifier first — which cannot start a second recording (`handleModifierPressed`'s long-press arming is guarded on `!stopOnAnyKeyEnabled`) and whose release is `.consumed` rather than a tap, so it cannot stop the current one either. `USER_GUIDE.md` §2 documents this for users.

## 2. The sidecar

`sidecar/` (TypeScript/Bun) is a separate local process the Swift app spawns and manages (`Sources/OpenType/SidecarClient.swift`), talking to it via `curl` over a Unix socket (not a native HTTP transport — see §7). It owns every actual ASR/text-generation call, plus a separate local memory store the Swift side doesn't share state with directly (see §4). See `sidecar/README.md` for how to run/test it standalone.

## 3. Agent Runtime (`/agent/run`)

Loop shape (`sidecar/src/agent/loop.ts`): assemble system prompt + task + context + memory terms → call the LLM with the assembled tool list attached → if the model requests a tool call, execute it and loop back; otherwise the model's text is the final result. A progress event (`thinking`/`tool_call`/`tool_result`/`done`/`error`) is emitted after every step for the Task List panel. Hard iteration cap: `MAX_ITERATIONS = 10` (`loop.ts`). Tool results are clamped at the source (~25k chars, `coreTools.ts`) and again by the loop (`clampToolResult`, 20k).

Built-in tools are **always available**, merged via `mergeToolSets` (`toolSets.ts`) on every run — since the 2026-08-13 core-tools batch (`docs/superpowers/specs/2026-08-13-b2-agent-core-tools-v2-design.md`) this is far more than the two memory tools. Three groups: **memory** (`opentype__remember_fact`, `opentype__consolidate_memory_now`, `sidecar/src/agent/builtInTools.ts`); **core local/web tools** (`sidecar/src/agent/coreTools.ts`): `opentype__bash` (`/bin/bash -lc`, default cwd = user home, ~60s timeout), `opentype__python` (`python3` via temp file), `opentype__read_file`, `opentype__list_dir`, `opentype__grep` (system `grep -rn -I`; default scope `~/Desktop` + `~/Downloads`, explicit path overrides), `opentype__web_search` (DuckDuckGo HTML scrape, no API key), `opentype__web_fetch` (fetch + HTML-to-text), `opentype__open_file` (execs `/usr/bin/open` so the macOS default app previews/plays the file — Preview, Word, QuickTime; this is the "让它打开预览/播放" path, and a UI side effect the agent may take directly since showing the file *is* the requested outcome); and **MCP tools** — since the 2026-08-14 batch's **P2-13** these come from the sidecar-persisted config (`mcp-servers.json`, written through `/config/mcp`, see §2 and `sidecar/src/agent/mcpConfigStore.ts`), with the `OPENTYPE_MCP_SERVERS` env var demoted to a zero-config dev fallback that saved config overrides entirely (`resolveMcpServers`; see `mcpClient.ts` for the stdio/streamable-HTTP connection itself). Connections are made once at sidecar boot, so a config change applies from the next start. **The v1 "no-side-effect tools only" policy is retired**: the agent deliberately has real hands (shell, Python, network) with no sandbox and no pre-execution confirmation — YOLO mode, an owner-accepted local risk. The entire merged set (memory + core + MCP) flows through an `ApprovalPolicy` seam (`withApproval`, `sidecar/src/agent/approval.ts`), and since the 2026-08-14 batch's **P1-6** that seam has a real prompting implementation. `server.ts` still wraps the shared set in `yoloApprovalPolicy` (the always-allow baseline, and what `/oneshot/ask` narrows down from — ask has no run to prompt through), but `handleAgentRun` wraps the *per-run* set — the same merged set plus that run's `opentype__ask_user` — in `createPromptingApprovalPolicy`, which needs the run's id, cancellation signal and question broker and so cannot be built at construction time. That policy asks `classifyCommandRisk` (`sidecar/src/agent/commandRisk.ts`, pure, one call's args, no filesystem) and lets everything it calls `safe` through untouched; a `destructive` call parks on the existing `ask_user` channel (`GET /agent/question/:runId`, `POST /agent/answer/:runId`) showing the command verbatim, and approve/deny/stopped/nobody-listening map onto the seam's four outcomes (`allowed-once` / `rejected` / `cancelled` / `unavailable`). A denial reaches the model as a normal tool-error result, so the run steers rather than crashing.

`destructive` means **named** destructive shell/python operations — `rm`/`find -delete`/`xargs rm`, the overwriting family (`mv`/`cp`/`rsync`/`tee`/`ln -f`, head-position only so `npm install` stays quiet), truncating `>` redirects, `dd`/`mkfs`/`truncate`, `chmod -R`/`chown -R`, `git push --force`/`reset --hard`/`clean -f`, `sudo`, `eval`, `curl | sh`, and python's `shutil.rmtree`/`os.remove`/`os.rename`/`subprocess.*`. Unreadable bash/python payloads (missing, wrong-typed, unbalanced quotes) also classify destructive. General python file writes deliberately do **not**: python's write surface is unbounded, so catching `open(p,"w")` and nothing else would prompt on the most common legitimate thing an agent script does while missing every other spelling — and a guard that fires often is one users learn to click through. MCP tools are unclassified by design (no args grammar for them; a card on every MCP call would be a permanent tax carrying no signal). So this narrows the blast radius of a *misheard* task; it is not a sandbox and not a boundary — no whitelist, no filesystem confinement, `bash setup.sh` runs a script nobody read. YOLO remains the stance for everything outside that named list. The final answer is still draft-only (clipboard, never auto-sent) — the delivery invariant is unchanged; what changed is that tool *calls* are no longer pretended to be side-effect-free.

**Pre-dispatch confirmation (P1-6, Swift side).** Before an Agent task reaches `/agent/run` at all, `AppModel.confirmDispatch` holds the transcript on the voice surface for `DispatchConfirmation.windowSeconds` (1.5s) with Esc to take it back — a pure seam (`Sources/OpenType/DispatchConfirmation.swift`) plus an `OverlayController` window with a countdown bar and its own Esc monitors. Not a modal: the default is proceed, and only Esc landing inside the half-open `[armedAt, deadline)` window cancels. Agent only — ask is draft-only and higher-frequency, transcribe already has P0-3's post-delivery correction window.

On the Swift side, an Agent dispatch is non-blocking: `AppModel.dispatchAgentRun` records a `.running` `AgentRunRecord` immediately and hands the actual `/agent/run` HTTP call to a detached, un-awaited `Task`, so a slow multi-step run never blocks a second recording (including a second Agent task) from starting. `agentRuns` (`AgentRunTracking.swift`) is an in-memory-only bounded history, capacity 50, oldest evicted first — not persisted to disk, distinct from the sidecar's own durable audit trail. It now also carries an optional `conversationId`, filled in once the run's response comes back, linking the in-memory record to its persisted conversation (see §9) — `/agent/run` is still a single blocking call, so a run in flight has no persisted conversation entry to show yet.

## 4. ASR: local MLX-Whisper

`sidecar/whisper/serve.py` runs a persistent local Python process (default model `mlx-community/whisper-small-mlx`, overridable via `OPENTYPE_WHISPER_MODEL`) that `sidecar/src/asr/whisperClient.ts` spawns once at sidecar startup and reuses for every `/asr/transcribe` request over its own Unix socket. Model loading has real multi-second latency; the sidecar doesn't block its own `/health` on it — only the first actual transcription request waits for the model to finish loading. There is no cloud ASR fallback. Since the 2026-08-15 batch (§C) `TranscriptionLanguage` (`Models.swift`) is no longer preview-only: `AppModel.transcribeRequestBody` puts its `whisperCode` (ISO-639-1, a different vocabulary from the `appleLocaleIdentifier` the live-caption preview uses) on every `/asr/transcribe` body, and both backends honour it. `automatic` sends **no `language` key at all** — absent means auto-detect, which keeps the default request byte-for-byte what it was before the field existed, so the setting is opt-in rather than a forced language. `.cantonese` maps to `"zh"`, not `"yue"`: whisper-small's tokenizer truncates Whisper's language table to its first 99 keys and `yue` is the 100th, so `serve.py` would 500 on every Cantonese request — re-measure if the default model changes.

For a packaged `.app`, `build-app.sh` bundles `sidecar/whisper-env/` (the Python venv) and `sidecar/whisper/` into the app's Resources, and `SidecarClient` points the sidecar at those absolute bundled paths via `OPENTYPE_WHISPER_PYTHON_BIN`/`OPENTYPE_WHISPER_SCRIPT_PATH` — a `bun build --compile` binary has no reliable way to locate the original source checkout at an arbitrary launch-time cwd.

### First-run visibility, and the model never gets lost (§E, 2026-08-15 batch)

Before this batch a first install was a blank screen. The installer mentions the ~460 MB download **in the terminal**; the app said nothing at all; and `serve.py` warmed the model *before* opening its socket, so during that download there was nobody to ask — install, grant, hold the hotkey, speak, release, and nothing, for minutes. Three changes close that, in order:

- **`serve.py` opens its Unix socket first, and loads the model on a background thread second** (`sidecar/whisper/serve.py`'s `main()`). The state that load has reached lives in `model_status.ModelStatus`, a small stdlib-only, lock-protected state machine (`downloading` → `loading` → `ready`, or `failed` with the real exception text) deliberately split into its own module because `serve.py` itself imports `numpy`/`mlx_whisper` at module scope and can't be unit-tested without the full MLX venv. `GET /status` reports a snapshot of it; `POST /transcribe` **waits** on `wait_until_ready()` rather than rejecting, because the audio is already recorded by the time the request arrives and refusing it would throw away words the user already spoke.
  - The HTTP server is `socketserver.ThreadingMixIn` over `UnixStreamServer`, not the bare single-request-at-a-time server it used to be — see the settled-decision note below for why that stopped being optional.
- **`GET /asr/status`** (sidecar) proxies that, adding the one state only the parent process can report (`starting`, meaning the python child hasn't come up yet — a connection-refused on its socket during the first second of a launch is not an error) and short-circuiting to `{state:"ready",backend:"remote"}` before ever touching the local socket when the saved Whisper config is `remote`.
- **Swift polls it** (`AppModel.startWhisperStatusPolling`, driven by the pure `WhisperStatusPolling`/`WhisperReadinessPolicy` types in `WhisperReadiness.swift`) once per launch, starting only once the sidecar itself is `.ready`, at a 1s interval with exponential backoff (capped, small failure budget) on transport failure, and — this is the headline design constraint — **stops for good at `.ready` and at `.failed`**, so this is not a resident timer answering a question the app already knows the answer to. Both the menubar popover and the unified voice surface (`OverlayController`) render a "preparing the speech model" banner exactly while `showsPreparingBanner` says so, with a determinate progress bar only when `fractionComplete` can be drawn (never a bar frozen at 0% for an unknown total — that is the blank screen wearing a costume) and the honest sentence otherwise. **Recording is never refused**: `WhisperReadinessPolicy.allowsRecording` is `true` for every state, asserted over `allCases`. What actually protects the recording is `transcribeTimeoutSeconds`: `SidecarClient.curlInvocation` gained a `timeoutSeconds` parameter (default unchanged, 300s, for every other call site), and `AppModel.transcribeLocally` is the one caller that raises it — to 1,800s while the model is `starting`/`downloading`/`loading` — because `serve.py` holds the transcription request open until the model is ready, and that only preserves the recording if the Swift side is still there when it arrives; the old flat 300s would have walked away mid-download and silently discarded words the user had already spoken. A `.failed` state keeps the ordinary 300s, since a failed load answers immediately rather than blocking.
- **The model itself is now user-choosable**: `GET`/`PUT /config/whisper-model` (see the endpoint table above), backing a Settings row with three presets. Settled decision: `PUT` reports `restartRequired: true` rather than restarting the whisper child — restarting mid-flight means killing a python process that may be blocking a queued transcription and re-downloading up to 3 GB before anything works again, a bigger and separately-reviewable change than this batch, so the panel says "takes effect on next launch" (the same convention the MCP panel already uses) instead.

**Settled decision: `ThreadingMixIn` is load-bearing, not a nicety.** A bare `UnixStreamServer` answers one request at a time. That was invisible while nothing called the whisper server concurrently — it stops being invisible the moment `/transcribe` blocks inside `wait_until_ready()` for the download/load to finish: a single-threaded server cannot also answer `/status` while that request is parked, so the one endpoint that exists to explain the wait becomes unreachable for exactly as long as the user is waiting on it. `sidecar/whisper/serve.py`'s `UnixHTTPServer` class docstring carries this reasoning; it is the precondition every other bullet above assumes holds.

**Cross-item coupling to watch:** `TranscriptionLanguage.cantonese` maps to `"zh"`, not `"yue"`, because whisper-small's tokenizer only knows Whisper's first 99 languages and `yue` is the 100th (measured 2026-08-15 against `mlx_whisper` 0.4.3) — mapping to `"zh"` was chosen over `"yue"` failing every single Cantonese request. That measurement was against the *default* preset only. Now that §E-4 ships a real model picker, the mapping is tied to whichever model is actually loaded, not just the `OPENTYPE_WHISPER_MODEL` env var this comment originally anticipated — `large-v3` accepts `yue` directly. Whoever changes `DEFAULT_WHISPER_MODEL` (`sidecar/src/asr/whisperModel.ts`) must re-measure this first; both `Models.swift`'s `whisperCode` and `whisperModel.ts`'s preset list carry cross-referencing comments so this doesn't quietly drift.

### Dictionary feedback into recognition (P0-1, 2026-08-14)

Until this batch the entity dictionary (§6) only ever reached the *LLM*; recognition itself was unaware of it, so a term the user had taught kept coming out wrong forever. `sidecar/src/asr/dictionaryBias.ts` closes that with two independent mechanisms, both pure functions, both applied in `asr/routes.ts` from a single per-request read of the dictionary (`buildAsrRoutes(transcribe, { listTerms })`, wired in `server.ts` to `store.allTerms()`; the read is per request, not captured once, so a term taught mid-session applies to the very next utterance):

- **`buildInitialPrompt`** renders the dictionary as a Whisper `initial_prompt` — a natural sentence (`可能出现的专有名词：PayPal、Anthropic。`) rather than a bare list, because Whisper consumes the prompt as if it were the *previous* transcript. Canonical spellings only (an alias in the prompt would coach the decoder toward the misspelling), confidence ≥ 0.6, capped at 24 terms and 200 characters with truncation only ever at a term boundary. Empty dictionary → empty string → the key is omitted entirely rather than sent as `""`. `whisper/serve.py` takes it as a percent-encoded **query parameter** (`/transcribe?initial_prompt=…`) — a header would have to be latin-1 safe and these terms are routinely CJK — and passes it to `mlx_whisper.transcribe(..., initial_prompt=…)`, whose signature was verified rather than assumed. **Local only:** the remote OpenAI-shaped transcription API has no equivalent, so `resolveTranscribe`'s remote branch ignores the option.
- **`applyAliasCorrections`** rewrites known alias → canonical in the transcript afterwards. This half applies to *both* backends and is the guaranteed one (the prompt is only probabilistic). Longest alias first; aliases under 2 characters skipped; an alias equal to its canonical (ignoring case) skipped; ASCII aliases match case-insensitively and require a word boundary, CJK aliases match as plain substrings. The scan is a **single left-to-right pass that never re-reads its own output** — load-bearing, not an optimization, because the dictionary is now written automatically (P0-2) and so mutually-referencing pairs (小蜜 → 小米 alongside 小米 → 小蜜) arise naturally; any sequence of `replaceAll` collapses such a sentence onto one term and iterating to a fixed point never terminates.

Two consequences worth knowing before touching this code. **Ties are decided explicitly**: two terms can claim the same alias (nothing prevents it, and automatic learning makes it reachable), so patterns are ordered by alias length → confidence → recency → canonical spelling. `allTerms()` is `SELECT * FROM entity_terms` with no `ORDER BY`, so ranking on arrival order would have made the same sentence transcribe differently after an unrelated write. And **prompt leakage is real**: measured on 2026-08-14, two seconds of digital silence transcribes as `""` with no prompt and as a garbled echo of the prompt's terms with one. A realistic microphone noise floor does not trigger it (Whisper's pre-existing near-silence hallucination, "Thank you.", appears identically with and without a prompt), so this needs an all-zero input — a muted or dead device — to surface. `condition_on_previous_text=False` was tested and does **not** suppress it; the echo happens inside the first decode window, which the prompt always conditions. Suppressing it properly means dropping segments on `no_speech_prob`/`avg_logprob`, retuning thresholds that also govern quiet speech. Not done; the length cap and canonical-only rule are what currently bound the damage.

## 5. Text generation: DeepSeek by default, now user-configurable

**Superseded by §11 below** (dated after this section was first written): `sidecar/src/provider/deepseek.ts` is no longer the *only* text-generation client. It's still the zero-config env-based default/fallback (`DEEPSEEK_API_KEY`/`DEEPSEEK_MODEL`/`DEEPSEEK_BASE_URL`, `sidecar/src/env.ts`, unchanged), and the packaged-app `sidecar.env` bundling story below is unchanged — but a user can now explicitly configure and save a different provider (Anthropic or any OpenAI-compatible endpoint) via Settings/the onboarding wizard, which takes precedence once saved. See §11 for the full design; this paragraph is kept for the packaged-app env-bundling detail, which is still accurate: `build-app.sh` copies the sidecar's `.env.local` into `Contents/Resources/sidecar.env`, and `SidecarClient.loadBundledEnvironment` reads it back at runtime as the fallback path's credential source.

`Sources/OpenType/ImmutableAuditStore.swift` audit events (`recognized`/`corrected`/`completed`/`cancelled`/`failed` — the `.corrected` case backs Review-mode voice-correction rounds, §8; one JSONL file, append-only, never rewritten) record `provider`/`model` labels that now reflect whichever backend actually served the request — `"mlx-whisper"`/`"deepseek"`/`deepseek-v4-flash` as the zero-config defaults, or the user's saved provider's own type/model once one is configured (`AppModel.sidecarTextProvider`/`sidecarTextModel`/`sidecarASRProvider`, computed from `llmConfigSummary`/`whisperConfigSummary`).

**One new field, `recordingEndedAt: Date?` (P2-12, 2026-08-14).** The event's full shape is `schemaVersion`/`eventId`/`requestId`/`createdAt`/`platform`/`status`/`mode`/`rawTranscript`/`effectiveInput`/`selectedContext`/`result`/`provider`/`model`/`error`/`supersedesEventId`, plus this one. Only `.recognized` carries it, and it holds the instant the recording stopped — captured in `AppModel.finishRecording()` right after `audioRecorder.stop()`, then threaded into `process(audioURL:recordingEndedAt:)` and onto that session's `.recognized` event. It exists because `.recognized` is stamped *after* ASR returns, so before this the trail could express only the post-ASR remainder of a session's duration; the span a user actually waits through (release the key → text appears, with MLX-Whisper's decode as its dominant term) had no representation at all. With it, `completed.createdAt − recognized.recordingEndedAt` is the end-to-end figure the statistics panel shows, and the difference between that and `.recognized → .completed` *is* the ASR cost — which is what makes a change like P0-1's `initial_prompt` visible instead of invisible.

It is **optional**, and that is what makes it a no-migration change: this file is append-only and never rewritten, so rows written before the field existed simply lack the key and decode as `nil` (`decodeIfPresent`; the synthesized encoder omits the key when `nil` rather than writing `null`). The one rule readers must follow is that `nil` means *no measurement*, not *zero*: `UsageStats` excludes those sessions from the latency average rather than averaging them in as 0s, since a missing measurement counted as zero drags the figure toward a flattering lie permanently and there is no way to notice it after the fact.

## 6. Memory: two separate systems

These do **not** share storage and should not be confused:

- **Swift-side** (`Sources/OpenType/AgentMemoryStore.swift`, `HistoryStore.swift`, `OwnerProfileAutoUpdater.swift`, `MemoryInsightsAnalyzer.swift`): local task history plus "Learned Preferences" auto-analysis. `HistoryStore` is a plain **JSON file** (`history.json`, 100-entry cap); `AgentMemoryStore` is the SQLite-backed store (task records, recomputed "Learned Preferences" every 100 recorded tasks). **The read side is gone rather than inert (2026-08-14 batch, P1-7):** the layer that had zero production callers — `entriesForPrompt`/`memoriesForPrompt`/`profileContextForPrompt`, all of `LocalMemoryRetriever.swift` (retriever + `LocalMemoryEmbedding` + `IndexedMemoryEvent`), and with them the `memory_embeddings` table and the NLEmbedding vector every recorded event used to be indexed into — was deleted. The product decision §11 asked for went the delete way: the sidecar's own store (below) is the one that actually reaches a prompt, and keeping a second, unwired one only made the next reader adjudicate it again. Nothing here is injected into Agent context, and the `/agent/run` body remains just `task + selectedText + conversationId` — the old "~12 most recent tasks budget injected into Agent-mode context" claim was never true in the wired code. `AgentMemoryStore` itself stays: task history, the "Learned Preferences" recompute, legacy-data sanitisation and history reset are all live. The "About Me" profile is still effectively dead data — its Settings editor was removed, so it is neither user-fillable nor injected (`ownerProfile`/`updateOwnerProfile` survive only for legacy-data sanitization; see §7).
- **Sidecar-side** (`sidecar/src/memory/`): a separate SQLite entity dictionary + free-text `owner_facts` (`MemoryStore.ts`) built from episodic events, with a consolidation ("dreaming") pass (`consolidator.ts`) that proposes/accepts canonical terms + aliases. **Consolidation now runs on its own (2026-08-14 batch, P1-7):** `memory/startupConsolidation.ts` consults the `shouldConsolidate` gate (≥12h since last run + ≥5 **eligible** unconsolidated events — see the transcribe exclusion below) once per launch, `STARTUP_CONSOLIDATION_DELAY_MS` (5 min) after the sidecar starts serving — one check, not a polling timer, guarded so two passes can never overlap, and swallowing any failure so a launch-time nicety can't take the sidecar down. `main()` holds only the one-line call; the decision lives in a testable seam, the same split `lifecycle.ts` uses. The manual triggers (`POST /memory/consolidate-now`, the `consolidate_memory_now` agent tool) still bypass the gate entirely. **All three modes now feed the episodic layer** (same batch): `/asr/transcribe` records `mode: "transcribe"` with the pre-correction ASR text as `rawTranscript` and the alias-corrected text as `correctedTranscript` — the one place in the product where a real mis-hearing/correction pair exists for free — and `/oneshot/ask` records `mode: "ask"` with `origin: "agent"` (its `result` is machine-produced text that may quote fetched web pages, so it must not enter consolidation labelled as the owner's own words). Both are best-effort and never fail their request; transcribe additionally skips empty/whitespace-only transcripts, so five accidental hotkey presses can't open the gate on nothing. `applicationName` is a placeholder (`"OpenType Transcribe"`/`"OpenType Ask"`, following `/agent/run`'s equally synthetic `"OpenType Agent"`) — the sidecar cannot know the frontmost app, and no wire-format change was made for it because `applicationName` never reaches the consolidation prompt. Managed from the macOS Settings "Memory" panel: since the 2026-08-14 batch (P0-4) the entity dictionary there is **editable, not read-only** — add (`POST /memory/terms`), inline edit (`PUT /memory/terms/:id`) and delete (`DELETE /memory/terms/:id`), alongside the owner-facts list (`GET`/`DELETE /memory/owner-facts`, the latter finally wired to a button) and the still-read-only run log (`/memory/consolidation-runs`). Every row renders its `origin` badge, since surfacing `untrusted` provenance is the point of P1-12's flag. Deletes are irreversible and confirmed with a dialog; there is still **no rollback UI** for a whole consolidation run (§11).

  **`origin` is promoted one way** (2026-08-14 batch): `upsertEntityTerm` — the single shared merge path — raises a merged row to `"owner"` when the incoming write is an owner write, and never downgrades an existing `"owner"`. The two owner writes are the panel's `POST /memory/terms` and P0-2's voice correction (`POST /transcribe/correct`); `remember_fact` (`"untrusted"`) and the dreaming pass (`"system"`) leave provenance alone. Without this, a term the owner personally vouched for would stay flagged untrusted forever, and a badge that survives review is noise users learn to ignore. Note the asymmetry: `PUT /memory/terms/:id` is a plain field patch and does **not** promote — editing an untrusted term in place leaves it untrusted.

Three routes now read this store, not two. `/asr/transcribe` reads `entity_terms` on every request to bias and correct recognition (§4's P0-1 note) — the dictionary's first non-LLM consumer, and the one that makes teaching a term visibly worth doing. The other two are the LLM paths described next; note that the ASR path deliberately filters by **confidence only, never by origin**, unlike the prompt paths below. That is not an oversight: `origin: "untrusted"` exists to gate what can reach an *instruction* channel, and biasing a decoder toward a spelling is a correction, not an instruction. Filtering ASR by origin would silently break the main way a user teaches OpenType a name, since `remember_fact` is one of the paths that writes them.

`/oneshot/ask` and `/agent/run` both pull a light memory context from the sidecar-side store (`sidecar/src/oneshot/memoryContext.ts`) before calling the LLM: a "Known terms: ..." line for entity terms *mentioned in this input*, **plus a "What you know about the user: ..." line carrying every `owner_facts` row of origin `"owner"`, injected unconditionally (not relevance-filtered)** — origin-gated by the P1-12 fix so untrusted/agent/system-origin facts are excluded, but all owner-authored facts are still included every time. This is not the fuller structured memory-profile prompt the old Swift-native `PromptBuilder` used to assemble (that file no longer exists). Each such call also appends a line to a local `context-debug.log` (`contextDebugLog.ts`, path via `OPENTYPE_CONTEXT_LOG_PATH`) recording the truncated (~200-char) input text and what context was matched — a persistent local record of ask/agent input not covered by the "reset input history" action. A third, separate table pair (`conversations`/`conversation_messages`, `sidecar/src/memory/conversations.ts`) holds Q&A/Agent multi-turn conversation history — see §9; it shares the same sqlite file as the entity dictionary but is conceptually distinct from both memory systems above (it's turn-by-turn chat history, not a fact/term store).

## 7. UI: Alfred-style menubar + window split

- **Menubar `NSPopover`** (`MenuBarPopoverView.swift`): compact mode-switcher only — pick transcribe/ask/agent, glance at sidecar/shortcut status. Opened from the status-bar icon.
- **The status-bar icon itself** (`MenuBarStatusIcon` in `OpenTypeApp.swift`) is a **template image**, so the state is carried by the shape and by nothing else (§L of the 2026-08-15 batch, 2026-08-15). It used to be a coloured rounded square with a white mode glyph knocked out of it and `isTemplate = false`, which meant the fill colour was the only thing saying what the app was doing: against the HIG for a menu bar extra, one flat square to a colour-blind user, and an opaque square that sat on the wallpaper rather than in a translucent or dark menu bar. The measurement that settled it is the one the test still runs — rasterise the icon and keep only its alpha channel, which is all a template image is — and under the old drawing idle, listening, processing, and all three modes came out **byte-identical**, because the square covered the canvas and the glyph was opaque on top of it. The mapping now spends its one glyph on whichever question is live: **at rest it draws `InputMode.symbol`** (the same shape as that mode's card in the popover — the standing decision that the menu bar answers 「下一次按下会做什么」 without opening anything), and **once something is happening the state takes the glyph over** — `waveform` listening, `ellipsis.circle` for all three working stages, `checkmark` delivered, `paperplane.fill` dispatched, `xmark` cancelled, `exclamationmark.triangle.fill` failed. `listening` cannot reuse `mic.fill` precisely because that is transcribe's *mode* glyph, which would make idle and recording the same picture in the mode people record in most; `ellipsis.circle` is enclosed rather than bare because a bare `ellipsis` is a third the optical weight of every other glyph and the icon appeared to vanish while it worked. The groupings are deliberate and named in the test: `transcribing`/`transforming`/`inserting` share one mark (a few hundred ms each, no user action depends on which), `success`/`copied` share one, `idle`/`modeChanged` share one because a mode announcement *is* the mode. The `switch` has **no `default:`**, so a new `ProcessingState` case fails to build rather than inheriting some other state's shape — a test cannot enumerate a case that does not exist yet. Colour survives in exactly one place, the HIG's own exception: `MenuBarStatusIcon.tint(for:)` returns `AppAccent.nsPrimary` while actually recording and `nil` everywhere else, applied as the *button's* `contentTintColor` since the image is a mask — and `nil` is what hands the icon back to the system's treatment (adapting to a light or dark menu bar, inverting while the popover is open). The running-Agent badge lost its numeral in the move and that is an improvement: it was a 9.5pt font in a 36px sprite, under 5 points on screen and unreadable even in colour, and a mask has no second colour to print it in. It is now a 5pt dot with a *cleared* ring around it (two opaque shapes that touch merge into one blob in a mask, so the separation has to be an absence), the glyph neither shrinks nor moves when it appears, and the count moved to the tooltip and the VoiceOver label — which are also now set per state rather than the constant `"OpenType"` they were, since the words are the only place the state exists as text. `Tests/OpenTypeTests/MenuBarStatusIconTests.swift` (22 cases) pins the mapping one state at a time and then compares the rendered masks, so 「可分辨」 is measured rather than asserted.
- **Real app window** (`RootView` in `Views.swift`, opened via the popover's gear button, a tapped Agent-completion notification, or `AppTab` selection): Home (setup checklist, last result), History (the local statistics panel + the record list, see below), **Q&A** and **Agent** (past conversations + continuation, §9 — replaces the old Settings "Task List" section), and Settings — interface language, transcription-language picker, personal dictionary, connection/permissions, the Memory panel (editable dictionary since P0-4, §6), the provider sections ("语音识别"/"AI 模型", §10), the **MCP server panel** (P2-13, below), and local data management (reset history / relearn preferences).

**The local statistics band (P2-12, 2026-08-14; extended by §D-3, 2026-08-15)** is the header of the **听写** page (`UsageStatsBand` in `DictationViews.swift`), above the day-grouped record list — the redesign moved it out of the old History tab's small panel, since the numbers are a summary *of* that list and belong at the top of it. (`Views.swift` still contains the pre-redesign `UsageStatsPanel`/`HistoryView` pair; nothing constructs them any more.) It shows one rolling 7-day window: words dictated, average end-to-end wait, response time, corrections per 100 words, and — added by §D-3 — 「词典已学会 N 个词」.

Two of those carry the learning loop. **每 100 字纠错 is drawn as a line, not a point**: `UsageStats.Summary.dailyCorrectionsPerHundredWords` is seven `Double?`s over the same buckets as the word bars, and `CorrectionTrendLine` strokes them with a plain `Path` in `DS` tokens (no charting dependency — §D-3 asks for exactly this). The optionality is the design: a day with words and no corrections is a real `0` and a point on the line, a day that delivered nothing is `nil` and a **gap**, and collapsing the two would make a weekend off read as "it got worse when I came back". A run of one day is drawn as a dot, because a single measurement has no segment and dropping it would hide the only number a new user has. **「词典已学会 N 个词」** counts rows of `AppModel.memoryTerms` through `DictionaryStats.counts(for:)` — rows, not aliases, so a term corrected three times reads as one learned word — and prints the owner's share separately (「其中 M 个来自你」), because `remember_fact` can write terms out of agent context with `origin: "untrusted"` (P1-12) and a blended total would let a number the user reads as 「what I taught it」 include rows nobody taught it. It is the figure that means something on day three, before there is enough history for a slope. 听写 refreshes just the terms (`AppModel.refreshMemoryTerms()`, split out of `refreshMemoryPanel()`) so opening the page costs one round trip rather than three.

Everything is computed at read time by `UsageStats` (`Sources/OpenType/UsageStats.swift`) from `audit-events.v1.jsonl`; there is no counter, no second store and no network path. A statistics feature that starts accumulating its own numbers is a second source of truth that disagrees with the audit log the first time one of them misses a write. `AppModel.refreshUsageStats()` recomputes on tab open and whenever the newest history entry changes (keyed on that entry's identity rather than on `entries.count`, which stops changing once the 100-entry cap is reached — i.e. for exactly the users who dictate most), doing the read and decode off the main actor in a detached task. That last part matters because the cost is O(whole file) every time and the trail is never trimmed: measured on this hardware, a 100k-event log (71 MB, roughly two years of heavy use) costs ~1.7s of background CPU and a few hundred MB of transient allocation per refresh, against ~0.17s at 10k events. Off the main actor that is battery rather than jank, and it is the reason the read may not be moved onto it; if it ever needs bounding, the fix is to decode only the file's tail back to the window start (~0.02s) rather than to start caching a second copy of the numbers. Malformed lines are skipped rather than fatal — the file is appended to with an open handle, so a crash can leave a half-written tail, and one bad line must not cost the user the week. Three rules the aggregator pins, each testable without a screen (`Tests/OpenTypeTests/UsageStatsTests.swift`, 33 cases; §D-3's series adds `UsageStatsTrendTests.swift`, 14): the unit is the **session** (`requestId`, counted iff it has a `.completed` event inside the window, attributed to that event's timestamp so a straddling session is counted whole on one side); words come from the *dictated* text only, never a model's answer and never a spoken correction instruction; and word counting is a **script-aware hybrid** — one word per CJK-family character, one per maximal alphanumeric run, applied per character rather than per whitespace token (中英混排 is typed without spaces) and with the CJK test *before* the alphanumeric one, since Swift reports `isNumber == true` for 一二十百千万 and the other order glues 「3万」 into one word. Deliberately not ICU's `.byWords` segmentation, whose dictionary-based Chinese splitting would report 「你好世界」 as 2 and would shift under the user with an OS update. Membership in the latency average is narrower than membership in the panel: a delivered session contributes its wait only if it carries a `recordingEndedAt`, is not an `agent` run, had no correction round before delivery, and yields a strictly positive span — the four cases where the difference on the clock is not the span the user waited (no measurement, no waiting, human editing time, and a clock that moved under the session via an NTP step or a sleep/wake), each excluded rather than zero-filled. And where a figure has no honest value the panel prints "—", never a zero: an absent latency, and the correction rate in a week with no dictated words at all, whose `0` is an empty denominator rather than a perfect score. The `recordingEndedAt` rule cuts one way only, and §D-3 pins it from the other side: rows that cannot express a span are excluded from the *timing* figures and from nothing else, so a mid-week upgrader's older days still count toward the trend line they are looking at.

**Superseded by §11 below.** The paragraph that used to be here described a deliberate *removal* of cloud-provider setup UI (old DashScope-era "Provider Vault" token entry, dead since ASR/text-generation moved to the sidecar). That removal was correct at the time, but has since been deliberately reversed by product direction: Settings now has real "语音识别"/"AI 模型" provider-configuration sections, and a first-run onboarding wizard gates entry into the app until both are configured. This is *not* a revival of the old Swift-side `AIServiceClient`/`AIProvider`/`ProviderVault`/`CredentialProvider` types (still dead, still removed) — the new system is sidecar-owned. See §11 for the full design. Setup readiness (the permissions/hotkey checklist this paragraph originally contrasted against) is unchanged by this — it's still just microphone + Accessibility + (optionally) Speech Recognition permissions, plus the hotkey registering successfully; provider readiness is a separate, additional gate (the onboarding wizard) layered in front of the whole app, not folded into this checklist.

**The MCP server panel (P2-13, 2026-08-14)** is the Swift half of the MCP config work whose sidecar half is in §2: a Settings section ("MCP 服务器", `McpServerPanelView` and friends in `Views.swift`, over `AppModel`'s "MCP server configuration" wrappers) that adds, edits, removes and tests MCP servers. It is deliberately built like the provider sections rather than as a new kind of surface — sidecar-owned config, Swift only calls the endpoints — and it closes the last step of the gap: `OPENTYPE_MCP_SERVERS` was the only way in, and a packaged `.app` user cannot set an env var.

Three things in it are load-bearing rather than cosmetic:

- **A mask can never be saved over a real secret.** The sidecar answers with `envMasked`/`headersMasked` only, so a real token never reaches Swift at all (`McpServerSummary` has no `env`/`headers` property to decode into). A saved secret is then seeded as `McpSecretEntry.stored(mask:)` and rendered as **static text** with a "已保存" tag — never inside a `TextField`/`SecureField`, so no amount of editing an unrelated field can carry the mask into a value the user reads as real. Its *key* is static for the same reason one level up: masks resolve per key sidecar-side, so renaming a key while keeping its mask would store the mask as that key's literal value. Replacing a secret is an explicit "更换" that opens an **empty** field, and a half-filled replacement blocks Save with a stated reason instead of silently writing an empty secret. Only the active transport's map is submitted, and the editor closes on a successful save, so every `.stored` mask on screen always corresponds to a secret the sidecar still holds under that same name and key. The mask round-trip itself (an untouched secret is submitted as its mask, which the sidecar resolves back) is what makes a *replace*-semantics `PUT` safe, and is pinned by `Tests/OpenTypeTests/McpServerCodingTests.swift`. One rule generalises all of that and is worth stating on its own: **a `.stored` entry is submitted byte-identical to how it arrived, key included** (`McpSecretEntry.submittedKey` trims a `.typed` key and leaves a `.stored` one alone). Any normalisation on this side — the review caught key-trimming doing exactly this — leaves the mask with no stored counterpart to match, and an unresolved mask is written as that key's literal value.
- **Test Connection is the decision, not a nicety.** It lists the tools the server would hand the agent — an unsandboxed capability grant — so the panel shows that list in full rather than as a count, and the section carries one unsoftened sentence saying those tools run on the user's Mac with no sandbox and that P1-6's prompting covers only *named* destructive calls in OpenType's **own** `bash`/`python` tools, never MCP ones. That last clause is load-bearing and was made explicit in review: `classifyCommandRisk` returns `safe` for every tool that is not `opentype__bash`/`opentype__python`, so a sentence that merely carved out "except a few destructive shell commands" would credit these tools with a guard that never fires for them.
- **Env-sourced rows are read-only.** When `source == "env"` the listed servers live in an environment variable, not in the store the routes address, so a `PUT`/`DELETE` would 404; they render with a "来自环境变量" badge, no edit/delete, and a line saying that saving anything here switches to the saved list entirely.

Errors split by where the user is looking, matching the provider panels rather than the memory panel: a failed **save** shows under the editor's own Save button (`McpServerEditor.saveError`, seeded from `AppModel.mcpEditError` and then cleared there via `clearMcpEditError()` so the sentence appears once, not twice), while the panel-level `mcpEditError` banner keeps the failures with no form to land in — a failed delete. Messages are the sidecar's own `{ error }` sentence where there is one (`AppModel.mcpFailureMessage` decodes the 400/404 envelope out of the decoding failure it arrives as), because "An MCP server named … already exists" names the field to fix and `ErrorMessagePresenter`'s generic 「本地服务响应异常」 would throw that away.

The panel also states the two operational facts a user would otherwise discover the hard way: connections are made once at sidecar boot, so a change applies after a restart; and a server should be tested before it is saved, because one that cannot be reached slows the next startup (see the boot-path hazard in §11 — a Swift-side warning is a mitigation, not the fix).

**开机自启 (§A of the 2026-08-15 batch, 2026-08-15).** Settings gained a 「通用」 group — its first, above 快捷键 — whose one row registers the app as a login item via `SMAppService.mainApp` (`Sources/OpenType/LaunchAtLogin.swift`). `LSUIElement` is already true, so this registers the app itself: no Dock flash at login, no helper bundle to ship or sign. The rule the whole seam turns on is that **the registration is the only source of truth**. `LaunchAtLoginController` re-reads the registrar on construction, inside `apply(desired:)` and on every `refresh()` — which has two callers, and needs both: the Settings page's `.task` (before its awaits) covers a window that was closed while the user was in System Settings, and `applicationDidBecomeActive` covers the window that stayed open, which is the ordinary way the `.requiresApproval` jump comes back. So a user who turns the login item off in System Settings while the app is running sees our switch follow either way, and a `register()` that launchd refused leaves the row reading 「关」 with its error — the next press being a real retry rather than a no-op, and the next re-read dropping the message, since it describes an attempt rather than a state. `AppConfiguration.launchAtLogin` persists only what the user last *chose*; it is never read to decide what the switch shows, and nothing reconciles it — re-registering at launch because it says `true` would undo the change the user just made in System Settings. `LaunchAtLoginStatus` keeps four cases where a `Bool` would do, because two of them are neither on nor off: `.requiresApproval` (macOS 13+, the user disabled our item in System Settings, after which `register()` neither throws nor takes effect) renders as a tinted row with a jump to Login Items rather than a switch that would sit on while the app never launches, and `.notSupported` (`SMAppService`'s `.notFound` — a debug build run out of `.build/`) explains itself instead of offering a control that could never take. Everything decidable without a screen lives in `LaunchAtLoginPolicy`'s two pure functions and is driven through a fake `LoginItemRegistering` (`Tests/OpenTypeTests/LaunchAtLoginTests.swift`, 23 cases); `SMAppService` itself is not exercised, and `SMAppServiceLoginItem` is thin enough that there is nothing in it to be right in a test and wrong in the app.

**更新检查 (§B of the 2026-08-15 batch, 2026-08-15).** 1.0.0 ships through a one-shot `curl -fsSL https://opentype-site.vercel.app/install | zsh`, so until now every bug in 1.0.0 stayed on every installed machine until its owner happened to re-run that line. `Sources/OpenType/UpdateChecker.swift` closes that, and **updates nothing**: it asks `api.github.com/repos/iyidgnaw/OpenType/releases/latest` for `tag_name`/`html_url`, and hands the user the same (idempotent) install command. No Sparkle — an auto-updater is a signing, hosting and appcast commitment, and what was missing is one sentence. The file is the repo's usual shape for anything touching a framework a test cannot drive: `compareVersions` and `UpdateCheckOutcome.from` are pure, the network call is an injected `@Sendable (URL) async throws -> (Data, Int)` closure, and `Tests/OpenTypeTests/UpdateCheckerTests.swift` (38 cases) never opens a socket. Four decisions are load-bearing. **Comparison is numeric, not lexicographic** — string ordering says `1.10.0 < 1.9.0`, which silently stops announcing updates the day a component reaches double digits — and tolerates a `v` prefix, a missing minor/patch, and a `-prerelease` suffix that sorts *before* its release. **`latest < local` is `.upToDate`**, because `CFBundleShortVersionString` is bumped in the commit that prepares a release, so every build between that commit and the pushed tag is ahead of `releases/latest`; the local version read is that key and never `CFBundleVersion` (`36`), which would compare `36` against `1.1.0` and kill the feature silently. **`check()` cannot throw**: HTTP status, transport error, unreadable body, missing or unparseable `tag_name` all resolve to `.unknown` with no retry — the unauthenticated API allows 60 requests/hour per IP, and answering a 403 with a retry storm turns 「静默失败」 into a ban. And **`.updateAvailable` carries the `v`-stripped display version**, which is the same form `AppConfiguration.lastSeenUpdateVersion` stores, so 「同一个版本只提示一次」 round-trips instead of re-nagging forever on a stored `v1.1.0`. Wiring: `AppModel.startUpdateCheckLoop()` runs one check 10s after launch (not competing with the sidecar coming up or a first-run Whisper model download) and one a day after that, guarded so a second loop can never exist; `changeUpdateCheckEnabled(false)` cancels it outright rather than hiding what it finds, since the switch exists because a periodic outbound request the user never asked for deserves to be refusable. The announcement lives on **the menubar popover** — a row above the footer with the version and a 「复制安装命令」 button — because the main window is `.accessory` and usually closed, so a notice only 设置 carries is one nobody sees; copying is also the acknowledgement, which is what writes `lastSeenUpdateVersion`. 设置's new 「关于」 group carries the other half for the user who came looking: version, the last result including a failed one, 「检查更新」 (which works even with the periodic check off — a pressed button is not a background request), and the switch. Nothing auto-downloads, nothing auto-installs, and nothing is ever modal.

**麦克风设备可见 (§K of the 2026-08-15 batch, 2026-08-15).** 设置's 「引擎」 group gained a fourth row, 「输入设备」, which names the system's current default input in mono beside 语音识别 / 语言模型 / Agent 工具 / 语音识别语言. `AudioRecorder` has always recorded from the system default and named nothing, so the failure in `docs/reviews/2026-08-15-product-review.md` §9 had no in-app answer: the AirPods come out, the default silently moves to the built-in microphone, the next dictation is markedly worse, and 「这产品变差了」 is the only conclusion available. **只显示，不做选择器** — an app-side picker would be a second source of truth for something the system owns, and would go on claiming a device the recorder is not using the moment the two drift; what was missing is diagnosis, not control. `Sources/OpenType/InputDevice.swift` is the repo's usual split: `InputDeviceSnapshot.system()` is the only code that touches `AVCaptureDevice`, `InputDeviceName.resolve(from:)` is pure, and `Tests/OpenTypeTests/InputDeviceNameTests.swift` (13 cases) drives the decision and the monitor without AVFoundation. ## 8. Direct vs. Tidy vs. Review transcribe mode

`transcribe` mode now has three variants, chosen by a persistent Settings toggle (`AppConfiguration.transcribeVariant`, `TranscribeVariant` in `Models.swift`, Settings' "转写" section) that applies to every `transcribe`-mode recording until changed — not a per-recording choice:

- **Direct** (default): hotkey → speech → the transcript is delivered immediately via the existing pipeline (clipboard + optional auto-insert). The delivery itself is still exactly the pre-existing `.transcribe` code path, with no added latency — but since the 2026-08-14 batch's **P0-3** it is followed by an 8-second correction window in which the hotkey offers to fix what was just delivered, in place. See "Direct's own correction affordance" below.
- **Tidy** (added by the 2026-08-14 batch's **P1-8**): identical to Direct except that the transcript passes through `TidyTranscript.tidy(_:)` first — filler removal (嗯/呃, 那个/就是说, um/uh/er), stutter collapsing, and punctuation/whitespace normalisation. **There is no LLM call, no sidecar call, and no provider requirement**: the rules are pure, synchronous Swift, so Tidy works with the network off and adds no measurable latency. That is the product promise, not an implementation detail — it is the tier between 「一字不改」 and 「问答」 for users who want cleaner text without their dictation reaching a model, and it is why "just ask the LLM to clean it up" is *not* an acceptable future refactor of this variant. Delivery, clipboard behaviour, and the P0-3 correction window are Direct's, unchanged.
- **Review**: hotkey → speech → the transcript is stashed in a floating, editable Review panel (`ReviewPanelController.swift`) instead of being delivered anywhere. Nothing is inserted or copied until the user explicitly commits.

### How the variant axis routes (P1-8)

`TranscribeVariant.deliverableText(for:)` is the single decision point: Direct returns the transcript, Tidy returns `TidyTranscript.tidy(transcript)`, Review returns `nil` meaning "staged, don't deliver yet" — the same "dispatched, don't wait" early-return path `.agent` uses. `AppModel.process(audioURL:)`'s `.transcribe` branch consults it and holds no opinion of its own about variants. Its companion `deliversIntoTargetApp` (true for Direct and Tidy, false for Review) is what the P0-3 correction window gates on, in both `CorrectionWindow.intent(...)` and `CorrectionWindow.reduce(...)`.

Tidy gets the correction window for a sharper reason than "it also delivers": it is the only variant whose output differs from what the user said, so a wrong word there can be OpenType's doing rather than only the recogniser's. Review stays excluded because its open panel already gives the second hotkey press a meaning.

**Audit**: a Tidy delivery writes the same event shape as any other — `rawTranscript` = what ASR heard, `effectiveInput` = what the user said after mode-routing, and the `.completed` event's `result` = the tidied text that was actually pasted. The cleaned form never overwrites `effectiveInput`, so both halves stay recoverable from the chain and the `.completed` event cannot contradict the `.recognized` event written earlier under the same `requestId`. `provider`/`model` stay `nil`, which for Tidy states that no model was involved rather than merely that a field is missing.

`TidyTranscript`'s own rules are documented in the file, which is worth reading before changing any of them: several are deliberately narrower than the feature brief that motivated them (`like` is not removed at all; 那个/就是说 need both a clause-leading position *and* a following mark; a two-character Chinese stutter is left alone because reduplication is grammatical). The governing asymmetry is that leaving a filler in is a cosmetic miss while deleting a real word is silent data loss.

Four narrowings came out of the stage-4 review, each closing a case where a rule that reads correctly rule-by-rule deleted or corrupted a real word (pinned in `TidyTranscriptFalsePositiveTests.swift`):

- **A filler that is a whole sentence is the utterance, not a hesitation.** 嗯 alone is 「yes」 and 那个 alone is 「that one」, so 「他问我明天去不去。嗯。」 and 「你要哪个？那个。」 kept their answers instead of losing them. A hesitation is by definition followed by the thing being hesitated about *inside the same sentence*, so requiring a sentence boundary on both sides separates the two shapes without touching 「嗯，我觉得可以。」. The exemption reads the **original** left neighbour rather than the output built so far — inheriting the clause-leading rules' promotion would exempt the last filler of an all-filler utterance and break idempotence.
- **A dot needs evidence on its right, too.** The widening guard only looked left, so a Chinese filename stem read as "Han character, then a full stop": 「打开 报告.pdf」 delivered 「报告。pdf」. A dot followed by an ASCII word character is inside a token (extension, domain, version), never a clause end.
- **Han numerals are values, not stutters.** The ≥3 collapse is Han-only precisely because repeated digits are a value, and Whisper writes a dictated 「二二二」 in Han as readily as in Arabic — 「我的房间是二二二号」 became 「二号」.
- **English repeats on purpose too.** The CJK side protected 哈哈哈 while "ha ha ha" collapsed to "ha" and "bye bye" to "bye"; the allowlist now exists on both sides.

### 按应用规则: the built-in per-app table (§J, 2026-08-15)

`Sources/OpenType/AppRules.swift` is a fixed, non-editable table keyed on the bundle identifier `ContextBridge.capture` already reads. That identifier has been carried end to end since long before this — `CapturedContext` holds it and `OutputDeliveryPolicy.shouldInsert` compares it against the frontmost app at delivery time — but until now it was only ever consulted to *downgrade* a delivery whose target had moved, never to say anything about the target itself.

`AppRule` has a `bundleIdentifier`, a `displayName` (for the Settings table, so the list on screen cannot drift from the list in force) and two optionals, `autoInsert: Bool?` and `transcribeVariant: TranscribeVariant?`, where `nil` means *no opinion, leave that decision where it was*. `AppRules.rule(for:)` answers `nil` for an unlisted app and for a `nil` identifier — not an empty rule, because "no opinion" has to be distinguishable at the type level from "an opinion that happens to match today's default". Three groups, and only the first is about safety:

- **Terminals** (`com.apple.Terminal`, `com.googlecode.iterm2`, `dev.warp.Warp-Stable`, `net.kovidgoyal.kitty`, `com.github.wez.wezterm`) do not receive an automatic insert. `ContextBridge.insert` is a clipboard write plus ⌘V, so a dictated sentence containing a newline is a command the shell runs the moment it lands — a reachable destructive path in the shipping configuration, and *less* supervised than anything the agent does, since `opentype__bash` at least passes through `classifyCommandRisk` first. These rows carry no variant opinion: they are a delivery rule, and changing what reaches the clipboard for a destination we already decided not to deliver into would be a second, unasked-for behaviour change riding along with a safety one.
- **Messaging and notes** (微信, 备忘录, Slack, Notion) default to Tidy — prose written to a person, where the 嗯/那个 and the restarted sentence are noise.
- **Code editors** (Xcode, VS Code, IntelliJ) default to Direct. Not redundant with the factory default even though it names the same value: it states the intent, and it is what keeps a future change to `AppRules.factoryTranscribeVariant` from silently reaching Xcode.

**Composition, delivery half.** The rule is applied at the existing seam rather than through a second delivery path: an overload `OutputDeliveryPolicy.shouldInsert(capturedBundleId:frontmostBundleId:perAppRulesEnabled:)`, declared in `AppRules.swift`. The pre-existing focus guard runs **first**, and a rule is only ever asked about a delivery the guard has already agreed to — so a rule can take an insert away and can never give one back. `perAppRulesEnabled` deliberately has no default value: a defaulted third parameter beside the existing two-parameter function is how the current call sites would silently pick up behaviour they never asked for. Only `AppModel.process`'s delivery branch calls the new form; `CorrectionWindow.intent` and `AliasUndo.decide` keep calling the two-argument one. That narrowing is not vacuous — `armCorrectionWindow` runs whether or not the insert landed, so a terminal dictation this table downgraded still arms a correction window whose follow-up would write through the same `ContextBridge.insert` — and closing it means threading the switch into those two call sites, which live in another item's files.

**Composition, variant half.** `AppRules.transcribeVariant(for:userSelected:perAppRulesEnabled:)`. A row fills an *unmade* choice and never overrules a made one: someone who went into Settings and chose 复核 did it because they want to see every transcript before it lands, and delivering straight into 备忘录 because a table prefers Tidy there is exactly the surprise they set that switch to prevent. The asymmetry with `autoInsert` is the governing rule — a row may **restrict** delivery on safety grounds (strictly less happens than was asked for, and the text is still on the clipboard) but may never **substitute** one behaviour for another the user picked.

"Explicit" means *the user chose*, not *the value differs from the factory default*, and making that decidable is the one change this needed outside the new file: `AppConfiguration.userSelectedTranscribeVariant` is a `TranscribeVariant?` that is `nil` until something readable has been stored under the key. Nothing extra is persisted for it — `didSet` does not fire during `init`, so a fresh install never writes the key and the first assignment from the UI creates it, including an assignment of `.direct`. Both it and the existing non-optional `transcribeVariant` come out of one `storedTranscribeVariant(in:)` parse, so an unreadable stored value (`polish`, from an older build) cannot be a choice to one reader and a variant to the other. `AppModel.process` resolves the variant once, from the app captured at recording time, and uses that same value for `deliverableText(for:)` and for `armCorrectionWindow`.

**The master switch** (`AppConfiguration.perAppRulesEnabled`, on by default) is read *inside* `shouldInsert` and inside the variant resolution rather than at their call sites, so "rules off" cannot be half-honoured by one caller and observed by another. Off is a total bypass: byte-for-byte the un-ruled decision for every pair of identifiers, terminals included. On by default because the terminal rows close a reachable destructive path and a safety default nobody can find in Settings protects nobody.

**Surfaced, not magic.** 设置 → 听写输出 carries the switch plus a read-only table of the defaults, grouped by effect rather than listed one app per row (three lines answer 「哪些应用不一样」; twelve rows of bundle identifier bury it), built from `AppRules.defaults` so it cannot describe a rule the app is not applying. Per-row user editing is deliberately out of this batch — first see whether the defaults need changing at all (review §14's judgement that a rules engine is the wrong shape to reach for this early). When a rule rather than the focus guard is what withheld an insert, the delivery notice names the app instead of reusing 「焦点已切换」, which would be telling the user something that did not happen.

### Why a Settings toggle, not a new `InputMode`

Review is a delivery-timing variant of `transcribe` (same ASR, same "preserve verbatim" semantics, same no-LLM character), not a new mode with its own prompt/behavior contract — so it's a second axis (`TranscribeVariant`) crossed with the existing mode enum, not a 4th `InputMode` case. Tidy joins the same axis on the same grounds: it changes how much deterministic local processing happens before delivery, and *not* whether a model sees the text, so it needs no prompt, no provider, and no mode of its own. This keeps `InputMode.visibleModes` (and everything keyed off it — the mode-cycle hotkey chord, `VoiceModeRouter`, the menubar `ModeGrid`) unchanged.

A per-invocation trigger (e.g. a hotkey chord meaning "this one recording, review it") was considered and deliberately not added: `GlobalHotKey`'s existing chord surface (hold/double-tap presets, plus recording-modifier+Tab to cycle mode — §1; the Option+Shift half of that chord was removed on 2026-08-14) is already dense, and every remaining unclaimed combination would either conflict with a preset or need its own discoverability affordance. The Settings toggle is simple, discoverable, and — per the task brief — required to work standalone regardless, so it was built as the only mechanism rather than half-building a second one.

### The correction flow, end to end

1. **Original dictation** (Review variant active): `AppModel.process(audioURL:)`'s `.transcribe` branch transcribes as normal, appends the usual `.recognized` audit event, then calls `beginReviewSession(...)` instead of delivering — this shows the panel (`reviewPanelState`) and records session bookkeeping (`ReviewSession`: `requestId`, the originally-captured `CapturedContext`, and the last audit event id for chaining). The panel is an `NSPanel` with `.nonactivatingPanel` + a `canBecomeKey` override — the same pattern `OverlayController` already establishes — so the app that was focused when dictation started stays frontmost the whole time the panel is open.
2. **Editing**: the panel wraps a real `NSTextView` (`ReviewTextView`, an `NSViewRepresentable` — SwiftUI's `TextEditor` selection-binding API needs macOS 14 and this app targets macOS 13) rather than mirroring text through `@Published` SwiftUI state on every keystroke. The user can type directly; the text view is the sole source of truth for "current text" once shown.
3. **Voice correction**: with the panel open, a second hotkey press means "correction for the panel's current selection," not "start a new dictation" — `AppModel.hotKeyPressed()` checks `reviewPanelState != nil` first and, if the panel has no text selected, gives immediate feedback (no wasted recording) rather than proceeding. Selection existence is checked *before* recording starts; the recording itself only captures the spoken instruction (ASR only — no `VoiceModeRouter`/mode-switch parsing applies to a correction recording). `processCorrection(audioURL:)` then calls the sidecar's new `POST /transcribe/correct` with the panel's full current text, the selection as a UTF-16 offset range, and the transcribed instruction; the response's `replacement` is spliced back into the `NSTextView` at the same offsets (`ReviewPanelController.applyCorrection`, via `TextSpanCorrection`) and the new span is re-selected so a follow-up correction can immediately target it again. Selecting the entire text and speaking a rewrite instruction (e.g. "rewrite this more formally") uses the identical mechanism with no special-casing — the endpoint doesn't distinguish "small span" from "whole text."
4. **Commit** (Enter button / **Cmd+Return**, not bare Return — see below) or **Cancel** (Escape / Cancel button / click outside the panel): commit inserts the panel's current text via the same `ContextBridge.insert(...)` Direct mode uses (always copies to clipboard too), records a `HistoryEntry`, and appends the session's final `.completed` audit event; cancel discards everything and appends a `.cancelled` event with no result.

**Why Cmd+Return, not bare Enter, for commit**: the panel is a real editable multi-line text view, where bare Return is expected to insert a newline (the user may want a multi-line corrected result). Overloading bare Return as "commit" would make it impossible to type a newline. Cmd+Return is the standard macOS resolution for exactly this conflict (Mail/Slack-style compose-and-send) and is shown next to a visible "写入 (⌘↩)" button; Escape is unambiguous (text views don't use it for anything) and is bound directly, both as a button and via `.onExitCommand`. This is a deliberate refinement of the task brief's "Enter to commit" framing, not a literal implementation of it.

### Audit chain, not a single event

Per session, `ImmutableAuditStore` now records more than one linked event, all sharing one `requestId` and chained via the (previously-scaffolded-but-unused) `supersedesEventId` field rather than a parallel logging structure:

- `.recognized` — the original dictation (already existed; reused as the chain's first link).
- `.corrected` (new `AuditEventStatus` case) — one per correction round. `rawTranscript` = the spoken instruction, `selectedContext` = the substring that was replaced, `effectiveInput` = the model's replacement, `result` = the full text after splicing — all existing fields, repurposed for this event kind rather than new ones being added.
- `.completed` (commit) or `.cancelled` (discard) — the session's final outcome, `supersedesEventId` pointing at the last correction (or the original `.recognized` event if there were no corrections).

A reader can replay the whole session — original text, every correction instruction and its result, and the final outcome — by following `supersedesEventId` from the terminal event backward, not just see the last state.

### Direct's own correction affordance: the post-delivery window (P0-3)

Review made corrections possible but charged for them up front — every dictation goes through a panel, whether it needed fixing or not. P0-3 (`docs/superpowers/specs/2026-08-14-product-batch-plan.md`) turns that from a global switch into an *afterwards*: Direct still delivers instantly, and for **8 seconds** after a delivery the hotkey changes meaning. If the target app has text selected at press time, pressing the hotkey means "voice-correct this selection" instead of "start a new recording."

- **In place, not back through a panel.** The first design re-opened the Review panel prefilled with the delivered text; that is wrong, because the text is already pasted into the target app — committing the panel would insert a second copy, and undoing the first paste with Cmd+Z is unsafe once the user has touched the keyboard at all in those seconds. `ContextBridge.capture()` already reads the selection and `ContextBridge.insert()` is Cmd+V, which natively *replaces* one, so in-place correction needs no undo, no panel, and no new write path. It also works on text OpenType never produced.
- **The decision is a pure seam.** `CorrectionWindow.swift` — `intent(...)` returns `HotKeyIntent.correctSelection`/`.startNewRecording`, and `reduce(_:on:)` moves a `CorrectionWindow.State` over `delivered`/`correctionSucceeded`/`correctionFailed`/`recordingStarted`/`cancelled`. The window is the half-open interval `[delivery, delivery + 8)`, so expiry needs no timer: a stale window behaves exactly like none. App identity is delegated to `OutputDeliveryPolicy.shouldInsert` rather than re-derived, since a correction writes through the very same insert path a delivery does and the two must not disagree.
- **It never steals the hotkey.** Window hot but nothing selected → ordinary new recording. Someone who wants to correct selects first; someone who just wants to say the next sentence must not be interrupted.
- **Delivering transcribe variants only** (Direct and, since P1-8, Tidy). Ask/Agent cards already give a second utterance the meaning "continue this conversation" (`VoiceFollowUp`), and Review's open panel already owns the hotkey. Both halves are enforced: `reduce` refuses to arm unless the delivery was `transcribe` + `variant.deliversIntoTargetApp` (and an ineligible delivery *closes* an open window), and `intent` re-checks the mode the user is in **now** — the two together are what stop a window armed in one mode from being spent in another. The gate asks `TranscribeVariant.deliversIntoTargetApp` rather than listing cases, so a fourth variant has to state whether it delivers instead of inheriting an answer.
- **`AppModel.hotKeyPressed()` decision order**: Review panel open → the existing panel-correction path, unchanged; else `CorrectionWindow.intent(...)` says `.correctSelection` → `beginInPlaceCorrectionRecording`; else → new recording, unchanged. The correction round records the instruction only (ASR, never `VoiceModeRouter`), sends the selection as `fullText` with the span `0..<utf16.count` to the same `POST /transcribe/correct`, pastes the `replacement` back over the selection, and copies to the clipboard per the always-copy invariant. Both correction paths share one `requestCorrection(fullText:range:instruction:)` helper.
- **The paste is re-checked at write time, not only at press time.** The selection is read when the hotkey is pressed, but the paste lands an ASR + `/transcribe/correct` round trip later — and `insert` is Cmd+V, which replaces whatever is selected *then*. So `processInPlaceCorrection` re-reads the target immediately before writing and refuses the paste unless the frontmost app still passes `OutputDeliveryPolicy.shouldInsert` **and** the live selection is still byte-identical to the one that was corrected; otherwise it downgrades to clipboard-only with a `lastDeliveryNotice` saying why. This is a strictly stronger guard than the delivery path's, which only re-checks the app: dictated text landing in the wrong window is bad, but a replacement derived from one span pasted over a *different* span destroys text the user never pointed at.
- **Audit**: one `.corrected` event per round, `supersedesEventId` pointing at that delivery's `.completed` event (or the previous round's `.corrected`) — the same chain shape Review uses, so a Direct correction is a link in the delivery's chain rather than an orphan. `AppModel` keeps those anchors in `CorrectionWindowSession` alongside the pure window state.
- **Lifecycle**: cleared on a new recording (`beginRecording`, the one choke point — deliberately *not* `beginCorrectionRecording`, whose round has to survive long enough to re-arm), on Esc, and by expiry; **re-armed with a fresh 8s** on a successful correction, because fixing two words in a row is common. A *failed* correction neither re-arms nor clears: the window keeps running on its original clock.
- **Visibility is the feature, not decoration.** 「用户看不见这个窗口，这个功能就等于不存在」. `OverlayHideBehavior` gained `.scheduleHideWithCorrectionHint(after:)` and `OverlayController.hideBehavior(for:correctionWindowArmed:)`; while a window is open, the `.success`/`.copied` toast stays up for the window's full duration (not 0.9s), carries `CorrectionWindow.hintText`, and runs a bar that empties exactly as the window does. The duration comes from `CorrectionWindow.windowSeconds` itself so the bar cannot promise time the hotkey will not honor. `AppModel` keeps `overlay.correctionWindowArmed` in step with the window through one setter (`syncCorrectionWindowAffordance`), and `scheduleIdle` takes a matching longer delay so the model's state does not fall back to idle and tear the hint down early.
- **The trap the compiler does not catch**: `OverlayHideBehavior` has two consumers in `OverlayController`. `presentLegacy`'s exhaustive `switch` fails to build if a new case is unhandled; `presentToast`'s `guard ... case .scheduleHide(let seconds)` does **not** — an unhandled case there compiles fine and silently stops the preempted unified voice surface from ever being restored. Both now read the delay from one `OverlayHideBehavior.scheduledHideDelay` accessor instead of matching a single case, so the next case added cannot reintroduce this.
- **Closes the loop with P0-2**: this path is the same `/transcribe/correct`, so a correction made in the user's own text field also teaches the entity dictionary — fix a term once, and the next transcription gets it right. Since §D-2 that is no longer silent (below).

### The learning loop, made visible (§D, 2026-08-15)

P0-1/P0-2/P1-8 closed a real loop in code — the dictionary biases ASR, corrections teach the dictionary, the next transcription is better — and **all three of its exits were silent**. A user corrected 「呸泡」 → PayPal, the next dictation spelled it right, and the only explanations available to them were "Whisper got lucky" and "something rewrote my words". Worse, a *wrongly* learned alias rewrote their words with no explanation and no way out but hunting through the 记忆 page. §D of `2026-08-15-product-batch-plan.md` (motivated by `docs/reviews/2026-08-15-product-review.md` §1) opens all three.

- **D-1, the rewrite report and its undo.** `/asr/transcribe` now returns `replacements` (§2's endpoint table). `AppModel.transcribeLocally` returns a `Recognition` (text + replacements) rather than a bare `String`; the two correction paths take `.text` only, since a spoken *instruction* is never delivered and its rewrites are not something the user is looking at. The delivery toast gains 「自动修正 N 处」 — **places, not distinct terms**, since each place gets its own undo control — expanding to one 「呸泡 → PayPal · 撤销并删除该词条」 row per rewrite.
- **The undo is where this item's value is, and it has three outcomes, not a bool.** `AliasUndo.decide` (`Sources/OpenType/LearningLoop.swift`, pure) returns `.restoreText(String)` or `.forgetTermOnly(.windowExpired | .targetApplicationChanged | .textNoLongerMatches)`, and **the term is deleted in every one of them** — the alias is wrong regardless of whether this particular paste can be taken back, and sending the user off to delete it themselves is the chore the feature exists to remove. Precedence is expiry → app → text, because expiry is the blocker that is unconditionally true and "go back to Notes" is a fix the user can actually act on. `.textNoLongerMatches` is the interesting one: the delivered text must carry exactly as many occurrences of the canonical as the report accounts for, or which one to restore is a guess — the user who said 「PayPal」 correctly once *and* was misheard once would otherwise have a correct word overwritten, which is strictly worse than the mis-transcription.
- **Its timing is borrowed, never re-derived.** `decide` takes a `CorrectionWindow.State?` and asks `isExpired(at:)` and `OutputDeliveryPolicy.shouldInsert` — the same two judgements P0-3 uses — and `AliasReplacementTests` asserts agreement across a matrix of instants and app pairs rather than restating 8 seconds. A second time limit for undo would drift from the real one and have to be adjudicated later. The report itself lives *on* `CorrectionWindowSession`, so it appears and disappears with the offer to act on it, and a delivery that arms no window (ask, agent, Review) reports nothing — those are exactly the deliveries whose rewrites an undo could never put back.
- **Restoring goes through the one write path.** `ContextBridge.selectTextEndingAtCaret(_:)` re-selects the delivered run via `AXSelectedTextRange` and then the ordinary `insert(_:)` (Cmd+V) replaces it. Without the selection step a paste would *append* the restored sentence to the one already there. Every condition in it is a refusal to guess — nothing already selected, the field's value still ending at the caret with exactly the delivered characters, the AX read succeeding outright — and a `false` is reported honestly (「已删除这条词典记录，但没能改回这次的文本」) rather than pasted anyway, which is what apps that expose no usable `AXValue` get.
- **D-2, 「已记住：呸泡 → PayPal」.** `CorrectionResponseBody.learned` had been decoded and read by nobody since P0-2. `LearnedTermNotice.notice(for:)` turns it into a sentence plus the canonical spelling a click reveals (the dictionary is keyed on the canonical; an alias would select nothing), returning `nil` for a correction that taught nothing — the majority case, and claiming 「已记住」 there would teach the user to distrust the one signal this adds. Both correction paths get it from the shared `requestCorrection`: the in-place path hangs it on the delivery toast that push raises (preempting that toast would cost P0-3's own affordance), and the Review path uses the panel's existing hint line, because the panel is on screen and holding the user's attention. On the toast the sentence is a **button**: clicking it opens 记忆 with the row scrolled to and tinted (`AppModel.revealMemoryTerm` → `highlightedMemoryTerm`, mirroring `focusAgentRun`'s scroll-and-highlight). §D-2 asks for that click on both paths and the Review panel does **not** have it yet — `ReviewPanelController.showHint` renders one plain `Text`, so that path shows the sentence and nothing to click. Known gap, not a disagreement with the plan.
- **What is deliberately not here**: the undo is offered for the eight seconds the correction window runs and not afterwards. Past that the entry is still deletable from 记忆 — what expires is the one-click offer, not the recourse.

### Sidecar: `POST /transcribe/correct`

New endpoint, `sidecar/src/transcribe/{routes,prompts}.ts`, TDD'd (`sidecar/test/transcribe/correct.test.ts`, 8 tests, confirmed red — `Cannot find module` — before implementation, green after). Takes `{ fullText, selectionStart, selectionEnd, instruction }` (offsets, not the selected substring alone, per the task brief's own reasoning: unambiguous even when the target phrase repeats elsewhere in the text) and returns `{ replacement }` — the caller splices it back in, the endpoint never sees or returns the rest of the document. Takes a bare `chat` function (same DI shape as `buildOneShotRoutes`); validates the selection range (400 on `start >= end`, out-of-bounds, or a blank instruction) before ever calling the LLM.

The endpoint originally had **no** `MemoryStore`/entity-dictionary dependency at all, deliberately, and was described here as pure dependency-light logic. The 2026-08-14 batch's **P0-2** broke that on purpose — a correction the user made by hand is the single best signal for what the dictionary should contain, and leaving it unrecorded meant the user re-corrected the same word forever. The store is now an **optional** second argument (`buildTranscribeRoutes(chat, deps?)`): omitted, behavior is byte-for-byte what it was, which is still how most of `correct.test.ts` exercises it; supplied (as `server.ts` does), a correction that passes the gate in `learnCorrection.ts` is also written to `entity_terms` as `alias → canonicalTerm` via the shared `upsertEntityTerm` merge path, at `category: "term"`, `confidence: 0.8`, `origin: "owner"`, and echoed back as `learned` for the UI.

That gate exists because `/transcribe/correct` serves two unrelated jobs with an identical request shape: fixing a mis-transcribed *term* ("呸泡" → "PayPal"), which is exactly what the dictionary wants, and rewriting a span of prose ("rewrite this more formally"), which would poison it. `shouldLearnCorrection` decides between them after the fact from the two strings alone — both sides non-empty and differing case-insensitively, both ≤ 24 UTF-16 code units, no newline in the replacement, the replacement not containing the selection (an expansion, not an alias), neither side pure punctuation/whitespace. It is a pure function, and conservative on purpose: a false negative costs one repeated correction, a false positive silently rewrites every future transcript. Learning is strictly **best-effort** — it runs after the correction has already succeeded, and every store touch is inside one `try`, so a corrupt or unwritable memory DB degrades to "learned nothing", never to a failed correction.

Offsets are UTF-16 code units on both ends of the wire — `NSTextView.selectedRange()`/`NSRange`/`NSString` on the Swift side and native JS string indexing (`.slice`) on the sidecar side use the exact same representation, so raw integers pass through with no re-encoding step that could introduce an off-by-N bug for text outside the Basic Multilingual Plane. `TextSpanCorrection.swift` (Swift) documents and unit-tests this; a sidecar test (`"uses UTF-16 code unit offsets..."`) checks the same contract from the other end.

### What was drawn from OpenTypeless, and what wasn't

Per `docs/references/opentypeless-stt.md`: OpenTypeless has no panel-based review/stash step and no voice-scoped span-correction endpoint — its closest analog is `SELECTED_TEXT_ADDON`, a prompt fragment appended when text is already selected in the *target app* at request time, always going through its single always-on "polish" LLM pass. Nothing here was ported directly. What *was* useful as a reference:

- The reference notes' framing of "faithful correction, not generative rewrite" as something OpenTypeless leaves to prompt wording alone, with no structural guard — this is exactly why `CORRECTION_SYSTEM_PROMPT` is scoped hard ("Return ONLY the replacement text for the selected span... Never change or repeat anything outside the selected span") and why the Swift side splices only the returned span back in by offset rather than trusting the model to return a whole corrected document — a structural guard OpenTypeless doesn't have anywhere in its pipeline.
- Confirms this feature is new ground, not an adaptation of existing prior art: OpenTypeless's own roadmap treats automatic/voice-driven personal-vocabulary correction as an unscheduled, unimplemented gap (see that doc's "Still a gap" section) — this feature's whole mechanism (select a span inside a *stashed, not-yet-delivered* result, speak a correction, splice in place) has no OpenTypeless equivalent to diverge from or borrow beyond the general "faithful, narrowly-scoped correction" principle above.

## 9. Conversation continuation (Q&A / Agent tabs)

Ask and Agent mode are one-shot by default (a fresh `/oneshot/ask` or `/agent/run` call with no history) but can continue a specific past exchange: the Q&A tab lists past Ask conversations (`GET /conversations?kind=ask`, most-recently-updated first); tapping one fetches its full thread (`GET /conversations/:id`) and marks it as `AppModel.focusedAskConversationId`. The next time Ask mode is dispatched by voice while that id is set, the request includes `conversationId`, and the sidecar replays the conversation's prior messages as real chat history (not a squashed context blob) before the new question — genuine multi-turn continuation, verified against a real DeepSeek call by asking a question that only resolves given the prior turn (e.g. "why do I like it?" after "my favorite language is Rust"). The Agent tab (`AppModel.focusedAgentConversationId`) works the same way, except prior turns are folded into the loop's `context` as a short "previous task / previous result" summary rather than a full message-array replay (Agent's loop message shape doesn't carry arbitrary history the same way).

Leaving the thread view or using the tab's "new conversation" affordance (`AppModel.startNewAskConversation()`/`startNewAgentConversation()`) clears the focused id, so the next dispatch starts fresh again. A tapped Agent-completion notification (`focusAgentRun(_:)`) now selects the Agent tab and opens that run's conversation thread directly, using the `conversationId` recorded onto its `AgentRunRecord` once the run completes (§3).

## 10. Provider configuration (Whisper local/remote, LLM Anthropic/OpenAI-compatible)

Added after this doc's original writing, deliberately reversing §5/§7's "no cloud-provider picker" state per explicit product direction. Full design:

**Whisper (ASR).** A Settings/onboarding choice between:
- `local` (default, unchanged) — the existing sidecar-managed MLX-Whisper process (§4).
- `remote` — implements OpenAI's audio transcription shape (`POST /audio/transcriptions`, `whisper-1`/`gpt-4o-transcribe`-family models), against a **user-supplied base URL**, not hardcoded to `api.openai.com` — so a self-hosted OpenAI-API-compatible transcription server works too. `sidecar/src/asr/remoteWhisperClient.ts`. This is an assumption worth revisiting if a different "remote Whisper" shape turns out to matter more in practice (e.g. a raw self-hosted `faster-whisper` server with a non-OpenAI-shaped API).

`server.ts`'s `resolveTranscribe` (used by `/asr/transcribe`, replacing the old always-local `whisperClient.transcribe` wiring) picks local vs. remote per request from the saved config; `asr/routes.ts`'s request/response contract is unchanged either way, verified by: (a) sidecar unit tests for `remoteWhisperClient.ts` against mocked fetch, (b) a live end-to-end check against the actual packaged app — switched a real running instance to `remote` with a deliberately-invalid endpoint, confirmed `/asr/transcribe` genuinely attempted the remote call (got a real connection-refused error, not a silent local fallback), then switched back to `local` and confirmed a real transcription request against real MLX-Whisper succeeded again immediately. No live "remote Whisper" account was available to verify a *successful* remote transcription end-to-end — that gap is real, tracked below.

**LLM provider.** A Settings/onboarding choice between:
- **Anthropic** (Messages API shape, `/v1/messages`) — `sidecar/src/provider/anthropic.ts`. Translates both directions: OpenAI-shaped tool defs/tool_calls/tool-result messages (the shape `agent/loop.ts` and this codebase's other providers use) into Anthropic's `input_schema`/`tool_use`/`tool_result` content-block shape and back, so `/agent/run`'s tool-calling loop works unmodified regardless of which provider is active.
- **OpenAI-compatible** (Chat Completions shape, `/chat/completions`) — `sidecar/src/provider/openaiCompatible.ts`. Covers DeepSeek, OpenAI itself, and self-hosted servers sharing this shape; structurally the same request/response handling as the original `provider/deepseek.ts` (which is untouched and remains the zero-config fallback client, not superseded).

Both implement a shared `LLMProviderClient` interface (`chat`/`testConnection`/`listModels`, `sidecar/src/provider/types.ts`), dispatched by type via `sidecar/src/provider/registry.ts`. `testConnection()` prefers `GET /models` (cheap, no generation cost); if that 404s (some minimal self-hosted servers only implement chat), it falls back to a 1-message chat call so a real-but-listing-less server still reports success. `listModels()` throws on failure, and callers (`provider/routes.ts`'s `POST /config/llm/models`) catch that and substitute a hardcoded `KNOWN_MODELS_FALLBACK` list per provider type (current common OpenAI/DeepSeek and Anthropic model names as of this writing) rather than leaving the picker empty.

**Config storage.** `sidecar/src/provider/configStore.ts`'s `ProviderConfigStore` persists both configs as **plaintext JSON** next to the sidecar's existing SQLite data directory (same directory convention as `dbPath`/`whisperSocketPath`), `chmod 600`'d after every write. Deliberately *not* Keychain-backed — see that file's doc comment for the full reasoning, briefly: (a) the sidecar already stores other locally-sensitive data (the memory SQLite DB) unencrypted, so this doesn't lower the app's existing trust bar, and (b) Keychain-on-Swift-side would reintroduce the exact credential-plumbing-through-env-vars-at-spawn-time coupling this rewrite's earlier cleanup pass removed, and would need re-spawning the sidecar (or a live env-reload mechanism that doesn't exist) on every key change. `chmod 600` is the mitigation actually available at this layer; a real remaining gap if the local machine account itself isn't trusted.

**"Configured" is explicit, never ambient.** `ProviderConfigStore`'s `llmConfigured`/`whisperConfigured` booleans are only set by an actual `PUT /config/llm`/`PUT /config/whisper` call completing — i.e. the user finished Test Connection + model pick + Save (LLM) or explicitly chose a Whisper mode and saved (local or remote). An ambient `DEEPSEEK_API_KEY` env var alone never flips either flag. `GET /config/status`'s `ready = llmConfigured && whisperConfigured` is what gates the onboarding wizard.

**HTTP surface** (`sidecar/src/provider/routes.ts`, all consumed by `AppModel.swift`'s "Provider configuration" section, never by raw Swift-side Keychain/file access): `GET /config/status`, `GET`/`PUT /config/llm`, `POST /config/llm/test`, `POST /config/llm/models`, `GET`/`PUT /config/whisper`, `POST /config/whisper/test`. Responses never echo a raw API key back — only a masked preview (`apiKeyMasked`, e.g. `sk-b...81ff`).

**Onboarding wizard.** `Sources/OpenType/ProviderSetupViews.swift`'s `OnboardingWizardView` replaces `RootView`'s normal tab content (Home et al.) whenever `AppModel.needsProviderOnboarding` (derived from `providerConfigStatus.ready`) is true, and disappears automatically the instant both are saved (no separate "Finish" action needed — saving refreshes `providerConfigStatus` reactively). The app auto-opens the real main window the first time a launch discovers onboarding is needed (`AppModel.init`'s post-sidecar-ready check, guarded to fire once per launch), since the wizard lives in that window alongside Settings, not in the compact menubar popover. It reuses `WhisperSetupContent`/`LLMProviderSetupContent` verbatim from Settings' "语音识别"/"AI 模型" sections — one implementation, not a parallel wizard-only copy.

**Verification.** Sidecar: full TDD red-then-green cycle for the new provider abstraction (`sidecar/test/provider/{openaiCompatible,anthropic,configStore,routes}.test.ts`, `sidecar/test/asr/remoteWhisperClient.test.ts`) — confirmed failing (missing module) before implementation, all green after; 211/211 sidecar tests pass overall. Swift: `swift build` + `swift test` (64/64) pass. Packaged app: `./scripts/build-app.sh` → fresh `open dist/OpenType.app`, confirmed `GET /config/status` on a config-reset state reports `{llmConfigured:false, whisperConfigured:false, ready:false}` (the wizard's trigger condition) against the real running packaged sidecar (not dev-mode `bun run`); ran `POST /config/llm/test`, `POST /config/llm/models`, and `PUT /config/llm` against a real live DeepSeek key (OpenAI-compatible path), all succeeded, and a subsequent `/oneshot/ask` call correctly routed through the newly-saved config and got a real DeepSeek response. The Anthropic code path was validated only via unit tests against mocked responses — no live Anthropic API key was available in this environment, so a real end-to-end Anthropic call (Test Connection, model listing, and especially the tool-calling translation in `/agent/run`) remains unverified against the real API. Tracked as a gap below.
