# OpenType 产品评审（2026-08-15）

> **范围**：产品视角的第二轮评审，针对 `main` @ `53414e4`（Release 1.0.0，即 2026-08-14/15 批次
> ——词典闭环 + 侧栏重设计 —— 合并之后）。前一轮见同目录 `2026-08-14-product-review.md`，
> 它的 P0/P1/P2 已基本执行完（计划与结果见 `docs/superpowers/specs/2026-08-14-product-batch-plan.md`）。
> **本轮只写那一批落地之后的新缺口**，不重复上一轮已经解决或已被明确否决的条目。

---

## 0. 结论

上一轮的核心叙事——「用得越久越准」——**在代码里闭上了，在用户眼里没有闭上**。
词典偏置 ASR、纠错自动入典、就地纠错窗口，三段都真的在跑；但整条链路对用户是**完全静默**的：
没有任何一个像素告诉用户「它刚刚学会了一个词」或「这句话它替你改对了」。

一个用户感知不到的留存钩子不是留存钩子。这是本轮最值得做的一件事，而且几乎不要成本。

第二个变化是**产品已经发布了**（1.0.0 + `curl | zsh` 官网安装）。发布把三类过去可以拖的问题变成了硬伤：
没有更新通道、没有开机自启、界面锁死中文而所有对外物料是英文。这些不是功能缺失，是**已装机用户会流失掉的路径**。

---

## 1. 学习闭环完全不可见（本轮第一优先级）

闭环的三个出口，一个都没有接到界面上：

- **入典结果被丢弃在 Swift 里**。`/transcribe/correct` 已按 P0-2 返回 `learned: { canonicalTerm, alias }`，
  `AppModel.swift:1538` 把它解码成 `CorrectionResponseBody.learned`——然后**零读取**。那段注释自己写明了
  「the 「已记住」 affordance that will surface it is a separate piece of work, so nothing reads this yet」。
  那件 separate work 就是这一条。
- **自动修正结果被丢弃在 sidecar 里**。`sidecar/src/asr/routes.ts:132` 是
  `applyAliasCorrections(text, terms).text` —— `.replacements` 在这一行就被扔掉，
  第 134 行只返回 `{ text: corrected }`。Swift 侧根本拿不到「本次替换了哪几处」。
- **统计面板没有这条曲线**。P2-12 的三个指标（字数 / 耗时 / 每百字纠错）里，唯一能证明闭环在收敛的
  是「每百字纠错次数在下降」，但面板只显示本周单点，没有趋势（current-state §11 已记为已知边）。

于是真实的用户体验是：他改了一次「呸泡」→「PayPal」；下一次识别对了；他以为**这次运气好**。
产品做了全部的工作，却没有拿到任何一分信用。

**建议**（三条都是小改动，建议一起做，分开做没有意义）：

1. 纠错成功的 toast 增加一行「已记住：呸泡 → PayPal」，点击可跳到记忆页那一行。
2. `/asr/transcribe` 把 `replacements` 一起返回；有替换时浮层上给一个极轻的「自动修正 N 处」标记，
   悬停/点击展开看改了什么。**必须可撤销**——把一次静默的确定性替换变成一次可见且可反悔的替换，
   否则一个学错的别名会持续污染输出而用户找不到原因。
3. 统计面板把「每百字纠错次数」从单点改成 7 天折线，并加一条「词典已学会 N 个词」。

> 注意第 2 条同时补上了一个当前**没有出口**的失败模式：别名一旦学错（P0-2 的入典门槛是纯启发式），
> 用户在输出里看到的是一个凭空出现的错词，而界面上没有任何东西解释它从哪来。今天唯一的修法是
> 自己去记忆页翻词典。

## 2. 「转写语言」仍然是假的（这不只是缺功能，是错误承诺）

设置里的 27 种语言选择器（`AppConfiguration.transcriptionLanguage`）**只影响 Apple 的实时字幕预览**，
对最终识别零影响：`sidecar/src/asr/` 全目录没有 `language` 字段，`sidecar/whisper/serve.py` 也不传。

上一轮 review 已经指出这条，批次计划明确写了「不在本批，单独处理」，然后**一直没有处理，而 1.0 已经发出去了**。
一个用户把它切到「English」，得到的仍然是带中文标点的结果，他会认为产品坏了——这比没有这个选择器更糟。

成本几乎为零：`2026-08-14-product-batch-plan.md` 里已经实测并记录了正确传法（`language` 不是
`mlx_whisper.transcribe` 的顶层参数，走 `**decode_options`）。

**要么接上，要么把这个控件改名为「实时字幕语言」并降到相应的位置。** 不能留在现在这个状态。

---

## 3. Whisper 模型：无 UI，且首次 460 MB 下载全程静默

两个问题叠在同一个地方，合起来构成整个产品**失败代价最高的一分钟**。

- **模型只有环境变量**。`serve.py:41` 的 `OPENTYPE_WHISPER_MODEL` 是唯一入口，打包版用户改不到——
  这和 MCP 服务器当初的问题一字不差，而 MCP 那条已经在 P2-13 解决了，这条没有。
  默认 `whisper-small` 的中文专有名词错误率就是用户的第一印象。词典偏置救得回**用过的词**，
  救不回**第一次说的词**，而第一印象恰恰全部由后者构成。
- **首启体验是一段黑屏**。安装脚本在终端里说了一句「The first thing you transcribe downloads a ~460 MB
  speech model」（`scripts/install-release.sh:384`），但**应用内没有任何进度指示**。用户装完、授权、
  按住热键、说完、松开——然后什么都没有发生。`whisperClient.ts` 里那句
  "local MLX-Whisper server is taking longer than expected to become ready" 也没有对应的用户可见文案。

**建议**：设置里加一个模型选择（small / medium / large-v3，标注体积与速度），下载走应用内进度条；
并且**在首次启动时就开始下载**，而不是等到第一次按热键——用户装完到第一次开口之间的那几分钟是白送的，
现在浪费掉了。这两件事必须一起做，只做选择器会让更多用户掉进同一个黑屏。

---

## 4. 没有任何更新通道（1.0 已发布，这是结构性缺失）

全仓库没有 Sparkle、没有版本检查、没有「有新版本」的任何提示；分发是一次性的 `curl | zsh`。

意味着 **1.0.0 里的每一个 bug 都会永久留在已安装用户的机器上**，除非他们自己想起来重跑安装脚本。
对一个正在快速迭代的产品，这比清单上任何单个功能都贵。

不需要 Sparkle：启动时查一次 GitHub releases 的 latest tag，与本地 `CFBundleShortVersionString` 比对，
不一致就在设置里显示一行 + 一个「复制安装命令」按钮。半天的工作量。

---

## 5. 没有开机自启

全仓库没有 `SMAppService`、没有 LoginItem。

一个「按住热键就能说话」的常驻工具，用户每次重启 Mac 之后都得自己想起来打开它。
每一次重启都是一次流失机会，而这是这份清单里**投入产出比最高**的一条
（`SMAppService.mainApp.register()`，几十行加一个设置开关）。

---

## 6. 「我选错了模式」没有出口

P1-5（ask + agent 合并）已被产品负责人明确否决，本轮**不重提合并**。但那条 review 指出的真实痛点没解决：
用户必须在开口之前预判「这件事需不需要工具」，而这是实现细节。

有一个不改模式数量、不改热键的小解法：**Ask 的结果卡片上加一个「交给助理去做」按钮**——
一次点击把同一个问题用完整工具集重跑，复用现有 `conversationId`。反向不需要（agent 跑完发现只是个问题，
没有代价），所以只做**单向升级**就够。

这把「选错了要重说一遍」变成「点一下」，而合并模式的那些代价一个都不用付。

---

## 7. 历史与会话：能搜，但搜不到正文；不能删单条，不能导出

- `HistoryStore` 是 100 条上限的 JSON，只有 `clear()`（全清），**没有单条删除**。
  用户说错一句敏感的话，唯一的补救是清空全部历史。
- 会话搜索只匹配标题——`SessionsViews.swift:98` 的注释自己承认了动机是
  「The magnifying glass has to do something」。而用户找一段旧口述时，记得的一定是正文里的某个词，
  不会是自动生成的标题。
- **没有导出**。一个 local-first 产品把用户数据锁在自己的 `history.json` 里，和定位正面冲突。
  导出（Markdown / JSON）应该是这个定位的必选项，不是加分项。

---

## 8. 没有「按应用」的行为规则

`bundleIdentifier` 已经全链路被捕获（`ContextBridge` → `OutputDeliveryPolicy` 的「前台变了就降级为剪贴板」），
但**只用于安全降级，从不用于行为**。数据结构已经在那儿了，只差一张表。

最该有的两条：

- **终端里默认不自动插入**。把一段带换行的口述粘进 Terminal/iTerm 可能直接执行——这是当前配置下
  真实可达的破坏路径，而且比 Agent 的 `opentype__bash` 更没人看着（那条至少还有 `classifyCommandRisk`）。
- **按应用选交付档**：微信 / 备忘录默认 `tidy`，代码编辑器默认 `direct`。
  `TranscribeVariant` 现在是全局开关，而它的最佳值明显是随应用变的。

---

## 9. 没有麦克风设备选择

`AudioRecorder` 直接用系统默认输入，没有任何设备 UI。戴 AirPods 开完会摘下来，系统默认输入变了，
用户不知道自己正在用哪个麦克风，只会觉得「今天识别特别差」。

最低成本版本：设置里**显示**当前输入设备名（不做选择器也行）。让用户能自己诊断，比让他猜强。

---

## 10. 界面锁死中文，而所有对外物料是英文

`OpenTypeL10n.text(_:english:)` 的函数体是 `return chinese`，全 App 钉死中文。
但——**670 个调用点已经全部带着写好的英文文案**，`Resources/Localization/en.lproj/Localizable.strings` 也在。

同时 README、官网、安装脚本全是英文。这个组合的结果是：一个英文用户读英文官网、跑英文安装脚本、
装完打开——一个全中文的界面。他会当场卸载。

英文文案已经写完了，缺的只是一个 locale 判断。这是这份清单里**离得最近的一次扩量**。
（注意 `en.lproj/Localizable.strings` 只有 72 行且已过期——里面还有「智能编辑分支」这种早已删除的
Prompt Studio 文案——真正的资产是那 670 个内联 `english:` 参数，做的时候以它们为准。）

深色模式同理但不同性质：产品负责人已明确决定「深色下也保持亮色系」（`2026-08-14-product-review.md` §6.4），
理由成立，本轮不翻。只记一句：1.0 发布之后，「系统深色而应用刺眼白」会成为一条稳定的用户反馈，
到时候要的是一份真正的深色配色交付物，不是一次颜色翻转。

---

## 11. MCP 启动阻塞仍未修 —— 唯一一条用户能把产品彻底弄坏且无法自救的路径

不是产品功能，但必须在产品清单里，因为后果是产品级的。

`current-state §11` 记录得很清楚：`connectConfiguredMcpServers` 在 `Bun.serve` 之前被 `await`、
按顺序连接、没有自己的超时（只有 MCP SDK 的 60s），而 Swift 侧 `waitUntilReady` 只给 5s。
一个保存了的、会挂起的 MCP server ⇒ sidecar 起不来 ⇒ **听写也用不了**（一个只想口述的用户被 Agent 配置搞死），
而且**无法从应用内恢复**——配置 UI 就在那个起不来的应用里，唯一出路是手工删 `mcp-servers.json`。

P2-13 上线时明确说了「留给下一轮 sidecar pass」。这就是下一轮。
按每个 server 加一个短超时即可，把「应用起不来」换成「Agent 少了几个工具」。

---

## 12. 状态仍然只靠颜色编码

`OpenTypeApp.swift:389` 的 `image.isTemplate = false`：菜单栏图标是彩色方块，状态纯靠颜色区分。
违反 HIG，色觉障碍用户不可分辨，且在浅色/深色菜单栏下表现不一致。
形状差异（点 / 波形 / 齿轮）比颜色差异便宜也更可靠。

## 13. 优先级建议

**立刻做（都在补已发布 1.0 的窟窿，且都是小改动）**

1. #1 学习闭环可见化（三条一起）—— 这是本轮的主线
2. #2 「转写语言」接上或改名 —— 错误承诺，不能留
3. #5 开机自启 —— 全清单 ROI 最高
4. #4 更新提示 —— 决定后面每一批能不能真正送达用户

**下一批**

5. #3 Whisper 模型 UI + 首启下载进度
6. #11 MCP 启动超时
7. #10 英文界面（文案已就绪）

**再之后**

8. #6 Ask → 助理升级按钮
9. #7 历史正文搜索 / 单条删除 / 导出
10. #8 按应用规则
11. #9 麦克风设备显示、#12 模板图标

---

## 14. 不建议做

- **不要做流式**。上一轮的判断依然成立，而且现在更成立：闭环刚闭上但用户看不见，
  先让「已经做到的事」被看见，比让「慢」变好看更值。
- **不要做云同步/账户**。与 local-first 正面冲突。
- **不要重提 ask/agent 合并**。已被否决；#6 是它的低成本替代。
- **不要加第四个模式**，也不要给按应用规则做成一套通用规则引擎——先硬编码两三条默认值，
  看看用户是不是真的会去改。

## 15. 值得肯定的

上一批把「用得越久越准」从一句愿景做成了真的在跑的代码，而且每一条决策的**理由**都写进了文档
（P1-7 排除听写进 consolidation 那一段，尤其是「延迟发送也是发送」的判断，是这批里最好的一个决定）。
本轮清单里最重的一条，恰恰是给这批已经做成的工作补上它应得的那份可见度。
