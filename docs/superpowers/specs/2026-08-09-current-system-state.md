# OpenType macOS: current system state (as-built reference)

Status: descriptive, not a design doc. This is a snapshot of what the macOS
client actually does as of 2026-08-09, after a from-scratch rewrite (old
6-mode system deleted, then cut to exactly 3 modes, MLX-Whisper added for
local ASR, and the UI split Alfred-style into a menubar popover + a real app
window). It supersedes the mode/architecture *content* of earlier specs in
this directory for "what does the system do right now" purposes — those
specs (`2026-08-08-system-boundaries-and-memory-v1-design.md`,
`2026-08-09-b1-b2-mode-surface-design.md`,
`2026-08-09-b2-agent-runtime-v1-design.md`) are left as-is as a record of how
the design got here, and are still useful for *why* things are shaped this
way, but their mode lists (4-6 modes, Polish/Translate/X Reply, per-provider
tool-calling requirements) are stale. This doc is scoped to macOS because
**macOS is now the only platform in this repo**: iOS (`Platforms/iOS`),
Android (`Platforms/Android`), and the cross-platform contract
(`Shared/OpenTypeContract.json`, `Shared/Schemas/`) were removed outright
(product decision, not an oversight) rather than reconciled with the macOS
rewrite — don't go looking for them, and don't treat any older doc's
references to them (this directory's earlier dated specs, git history) as
describing current repo contents.

## 1. The 3 modes

`InputMode` (`Sources/OpenType/Models.swift`) has exactly three cases:

| Mode | Selection needed? | What happens | Sidecar call |
| --- | --- | --- | --- |
| `transcribe` | No | What MLX-Whisper hears is the result. **No LLM involved at all** — in any of its three delivery variants (§8): Direct delivers it verbatim, Tidy cleans it with deterministic local rules, Review stages it for the user to edit. | `/asr/transcribe` only |
| `ask` | No | Speaks a question; answered directly in the unified voice surface — the one bottom-center floating panel (`OverlayController`) that the listening HUD morphs into a result card (spec: `2026-08-13-hud-morph-result-surface-design.md`; the old center-screen `AskPanelController` popup is gone). The one mode that *answers* rather than preserves/transforms the input. If the Q&A tab has a conversation open (see §9), the question continues that thread instead of starting a fresh one-shot call. | `/asr/transcribe` then `/oneshot/ask` |
| `agent` | No | Speaks a task; dispatched non-blockingly to a tool-calling agent loop. Live step ticker + result card in the same unified voice surface as `ask` (dismissing it never cancels the run), plus the durable Agent tab record (§7/§9) and a completion notification. Same conversation-continuation behavior as `ask` if the Agent tab has a thread open. | `/asr/transcribe` then `/agent/run` |

Every mode's result is always copied to the clipboard (`OutputDeliveryPolicy.retainsClipboardCopy`, unconditionally `true`). Auto-insert into the currently-focused field is a separate, additional delivery step gated on the `automaticallyInsert` setting — never a replacement for the clipboard copy. No mode ever presses Return for the user: the spoken "发送 / press enter" command was removed outright (see §7), so `ContextBridge.insert(_:)` only ever pastes. `agent` in particular is draft-only, since a tool call inside the loop is itself an external action the instant it runs — this is a policy backstop, not a technical sandbox (see §6).

Mode switching is explicit — the mode-cycle chord, the menubar popover's `ModeGrid`, or a spoken mid-recording trigger ("agent 模式" / "agent mode" / etc., `VoiceModeRouter`) — never automatic classification of an ambiguous utterance.

**The mode-cycle chord (rewritten 2026-08-14, closing review items §6-7 and §6-9):** one rule — *hold the configured recording modifier, tap `Tab`*. Three defects made it effectively dead before, and all three are fixed:

- `AppModel.cycleMode()` opened with `guard state != .listening` — but holding the recording modifier is what *starts* a recording, so past the 300ms long-press threshold every cycle was rejected. `.listening` is now the gesture's main case, gated through `ModeCyclePolicy.allows` (only the mid-pipeline states `.transcribing`/`.transforming`/`.inserting`, plus `isBusy`/`isStartingRecording`, still refuse).
- Both the Tab gate and the old Shift half of the chord were hardcoded to left Option, so `fn` and double-tap users could never switch at all. The gate is now `GlobalHotKey.shouldCycleModeOnTab(heldModifierKeyCodes:preset:)`, which reads the active preset's own `modifierKeyCodes(for:)` set. The Space-chord presets register a Carbon hot key rather than the modifier-only event tap and so have no Tab handling — `usesModifierOnlyEventTap` is what says so, and `HotKeyPreset.modeSwitchHint` (the popover's hint copy, previously a hardcoded "点 Shift 或 Tab" string for every preset) is `nil` for exactly those.
- **The Shift half of the chord is removed outright** — Tab is the only mode-switch key now.

Cycling while `.listening` **retargets the in-flight recording**: `ModeCyclePolicy.cycle` moves `activeMode` as well as `configuration.selectedMode`, so the recording the user is still speaking into is processed as the new mode. (Retargeting mid-flight is not new — `VoiceModeRouter` already reassigns `activeMode` after transcription.) That path deliberately does *not* go through `selectMode(_:)`, whose `.modeChanged` toast would cover the live pill for 1.2s; it re-derives the surface instead, and since `voiceSurfaceMode` is `activeMode ?? surfaceRunMode ?? selectedMode`, the listening pill itself shows the new mode.

Tab **cancels nothing** (`GlobalHotKey.modeSwitchTabEffects`: `cancelsPendingLongPress` and `marksChordUsed` are both `false` — either one alone aborts the hold-to-talk the user is still holding for), so hold length rather than reaction time decides the outcome: release before the threshold and only the mode switched; keep holding and the recording proceeds as the new mode. Two things survive that removal: the `DoubleTapDetector` sequence is still reset at Tab time (a stale tap could otherwise fire an unrequested double-tap recording on the next tap), and a replacement flag `modeSwitchDidCycle` takes over `modifierChordWasUsed`'s other job of suppressing the release gesture — routed through the pure `GlobalHotKey.releaseGesture(longPressDidArm:modeSwitchDidCycle:chordWasUsed:)`, where an armed long press always wins. Tab is always swallowed, autorepeat included, so it never leaks into the focused app.

The chord branch sits **ahead of the stop-on-any-key branch** in `handleEventTap`, so while the recording modifier is held Tab means "switch mode", never "commit this recording". The converse is the one asymmetry worth knowing: during a *hands-free* (double-tap-started) recording the user's hand is off the modifier, so a bare Tab falls through to stop-on-any-key and commits. Cycling mid-recording there means pressing and holding the modifier first — which cannot start a second recording (`handleModifierPressed`'s long-press arming is guarded on `!stopOnAnyKeyEnabled`) and whose release is `.consumed` rather than a tap, so it cannot stop the current one either. `USER_GUIDE.md` §2 documents this for users.

## 2. The sidecar

`sidecar/` (TypeScript/Bun) is a separate local process the Swift app spawns and manages (`Sources/OpenType/SidecarClient.swift`), talking to it via `curl` over a Unix socket (not a native HTTP transport — see §7). It owns every actual ASR/text-generation call, plus a separate local memory store the Swift side doesn't share state with directly (see §4). See `sidecar/README.md` for how to run/test it standalone.

## 3. Agent Runtime (`/agent/run`)

Loop shape (`sidecar/src/agent/loop.ts`): assemble system prompt + task + context + memory terms → call the LLM with the assembled tool list attached → if the model requests a tool call, execute it and loop back; otherwise the model's text is the final result. A progress event (`thinking`/`tool_call`/`tool_result`/`done`/`error`) is emitted after every step for the Task List panel. Hard iteration cap: `MAX_ITERATIONS = 10` (`loop.ts`). Tool results are clamped at the source (~25k chars, `coreTools.ts`) and again by the loop (`clampToolResult`, 20k).

Built-in tools are **always available**, merged via `mergeToolSets` (`toolSets.ts`) on every run — since the 2026-08-13 core-tools batch (`docs/superpowers/specs/2026-08-13-b2-agent-core-tools-v2-design.md`) this is far more than the two memory tools. Three groups: **memory** (`opentype__remember_fact`, `opentype__consolidate_memory_now`, `sidecar/src/agent/builtInTools.ts`); **core local/web tools** (`sidecar/src/agent/coreTools.ts`): `opentype__bash` (`/bin/bash -lc`, default cwd = user home, ~60s timeout), `opentype__python` (`python3` via temp file), `opentype__read_file`, `opentype__list_dir`, `opentype__grep` (system `grep -rn -I`; default scope `~/Desktop` + `~/Downloads`, explicit path overrides), `opentype__web_search` (DuckDuckGo HTML scrape, no API key), `opentype__web_fetch` (fetch + HTML-to-text), `opentype__open_file` (execs `/usr/bin/open` so the macOS default app previews/plays the file — Preview, Word, QuickTime; this is the "让它打开预览/播放" path, and a UI side effect the agent may take directly since showing the file *is* the requested outcome); and **MCP tools** — since the 2026-08-14 batch's **P2-13** these come from the sidecar-persisted config (`mcp-servers.json`, written through `/config/mcp`, see §2 and `sidecar/src/agent/mcpConfigStore.ts`), with the `OPENTYPE_MCP_SERVERS` env var demoted to a zero-config dev fallback that saved config overrides entirely (`resolveMcpServers`; see `mcpClient.ts` for the stdio/streamable-HTTP connection itself). Connections are made once at sidecar boot, so a config change applies from the next start. **The v1 "no-side-effect tools only" policy is retired**: the agent deliberately has real hands (shell, Python, network) with no sandbox and no pre-execution confirmation — YOLO mode, an owner-accepted local risk. The entire merged set (memory + core + MCP) flows through an `ApprovalPolicy` seam (`withApproval`, `sidecar/src/agent/approval.ts`); the only shipped policy is `yoloApprovalPolicy` (always allow), and the seam exists so a future user-prompting (popup approve/deny) policy can slot in without restructuring. The final answer is still draft-only (clipboard, never auto-sent) — the delivery invariant is unchanged; what changed is that tool *calls* are no longer pretended to be side-effect-free.

On the Swift side, an Agent dispatch is non-blocking: `AppModel.dispatchAgentRun` records a `.running` `AgentRunRecord` immediately and hands the actual `/agent/run` HTTP call to a detached, un-awaited `Task`, so a slow multi-step run never blocks a second recording (including a second Agent task) from starting. `agentRuns` (`AgentRunTracking.swift`) is an in-memory-only bounded history, capacity 50, oldest evicted first — not persisted to disk, distinct from the sidecar's own durable audit trail. It now also carries an optional `conversationId`, filled in once the run's response comes back, linking the in-memory record to its persisted conversation (see §9) — `/agent/run` is still a single blocking call, so a run in flight has no persisted conversation entry to show yet.

## 4. ASR: local MLX-Whisper

`sidecar/whisper/serve.py` runs a persistent local Python process (default model `mlx-community/whisper-small-mlx`, overridable via `OPENTYPE_WHISPER_MODEL`) that `sidecar/src/asr/whisperClient.ts` spawns once at sidecar startup and reuses for every `/asr/transcribe` request over its own Unix socket. Model loading has real multi-second latency; the sidecar doesn't block its own `/health` on it — only the first actual transcription request waits for the model to finish loading. There is no cloud ASR fallback and no per-request language hint sent to Whisper (it auto-detects); `TranscriptionLanguage` (`Models.swift`) survives only as the Apple on-device live-caption *preview's* locale, unrelated to the real transcription.

For a packaged `.app`, `build-app.sh` bundles `sidecar/whisper-env/` (the Python venv) and `sidecar/whisper/` into the app's Resources, and `SidecarClient` points the sidecar at those absolute bundled paths via `OPENTYPE_WHISPER_PYTHON_BIN`/`OPENTYPE_WHISPER_SCRIPT_PATH` — a `bun build --compile` binary has no reliable way to locate the original source checkout at an arbitrary launch-time cwd.

### Dictionary feedback into recognition (P0-1, 2026-08-14)

Until this batch the entity dictionary (§6) only ever reached the *LLM*; recognition itself was unaware of it, so a term the user had taught kept coming out wrong forever. `sidecar/src/asr/dictionaryBias.ts` closes that with two independent mechanisms, both pure functions, both applied in `asr/routes.ts` from a single per-request read of the dictionary (`buildAsrRoutes(transcribe, { listTerms })`, wired in `server.ts` to `store.allTerms()`; the read is per request, not captured once, so a term taught mid-session applies to the very next utterance):

- **`buildInitialPrompt`** renders the dictionary as a Whisper `initial_prompt` — a natural sentence (`可能出现的专有名词：PayPal、Anthropic。`) rather than a bare list, because Whisper consumes the prompt as if it were the *previous* transcript. Canonical spellings only (an alias in the prompt would coach the decoder toward the misspelling), confidence ≥ 0.6, capped at 24 terms and 200 characters with truncation only ever at a term boundary. Empty dictionary → empty string → the key is omitted entirely rather than sent as `""`. `whisper/serve.py` takes it as a percent-encoded **query parameter** (`/transcribe?initial_prompt=…`) — a header would have to be latin-1 safe and these terms are routinely CJK — and passes it to `mlx_whisper.transcribe(..., initial_prompt=…)`, whose signature was verified rather than assumed. **Local only:** the remote OpenAI-shaped transcription API has no equivalent, so `resolveTranscribe`'s remote branch ignores the option.
- **`applyAliasCorrections`** rewrites known alias → canonical in the transcript afterwards. This half applies to *both* backends and is the guaranteed one (the prompt is only probabilistic). Longest alias first; aliases under 2 characters skipped; an alias equal to its canonical (ignoring case) skipped; ASCII aliases match case-insensitively and require a word boundary, CJK aliases match as plain substrings. The scan is a **single left-to-right pass that never re-reads its own output** — load-bearing, not an optimization, because the dictionary is now written automatically (P0-2) and so mutually-referencing pairs (小蜜 → 小米 alongside 小米 → 小蜜) arise naturally; any sequence of `replaceAll` collapses such a sentence onto one term and iterating to a fixed point never terminates.

Two consequences worth knowing before touching this code. **Ties are decided explicitly**: two terms can claim the same alias (nothing prevents it, and automatic learning makes it reachable), so patterns are ordered by alias length → confidence → recency → canonical spelling. `allTerms()` is `SELECT * FROM entity_terms` with no `ORDER BY`, so ranking on arrival order would have made the same sentence transcribe differently after an unrelated write. And **prompt leakage is real**: measured on 2026-08-14, two seconds of digital silence transcribes as `""` with no prompt and as a garbled echo of the prompt's terms with one. A realistic microphone noise floor does not trigger it (Whisper's pre-existing near-silence hallucination, "Thank you.", appears identically with and without a prompt), so this needs an all-zero input — a muted or dead device — to surface. `condition_on_previous_text=False` was tested and does **not** suppress it; the echo happens inside the first decode window, which the prompt always conditions. Suppressing it properly means dropping segments on `no_speech_prob`/`avg_logprob`, retuning thresholds that also govern quiet speech. Not done; the length cap and canonical-only rule are what currently bound the damage.

## 5. Text generation: DeepSeek by default, now user-configurable

**Superseded by §11 below** (dated after this section was first written): `sidecar/src/provider/deepseek.ts` is no longer the *only* text-generation client. It's still the zero-config env-based default/fallback (`DEEPSEEK_API_KEY`/`DEEPSEEK_MODEL`/`DEEPSEEK_BASE_URL`, `sidecar/src/env.ts`, unchanged), and the packaged-app `sidecar.env` bundling story below is unchanged — but a user can now explicitly configure and save a different provider (Anthropic or any OpenAI-compatible endpoint) via Settings/the onboarding wizard, which takes precedence once saved. See §11 for the full design; this paragraph is kept for the packaged-app env-bundling detail, which is still accurate: `build-app.sh` copies the sidecar's `.env.local` into `Contents/Resources/sidecar.env`, and `SidecarClient.loadBundledEnvironment` reads it back at runtime as the fallback path's credential source.

`Sources/OpenType/ImmutableAuditStore.swift` audit events (`recognized`/`corrected`/`completed`/`cancelled`/`failed` — the `.corrected` case backs Review-mode voice-correction rounds, §8; one JSONL file, append-only, never rewritten) record `provider`/`model` labels that now reflect whichever backend actually served the request — `"mlx-whisper"`/`"deepseek"`/`deepseek-v4-flash` as the zero-config defaults, or the user's saved provider's own type/model once one is configured (`AppModel.sidecarTextProvider`/`sidecarTextModel`/`sidecarASRProvider`, computed from `llmConfigSummary`/`whisperConfigSummary`).

## 6. Memory: two separate systems

These do **not** share storage and should not be confused:

- **Swift-side** (`Sources/OpenType/AgentMemoryStore.swift`, `HistoryStore.swift`, `OwnerProfileAutoUpdater.swift`, `MemoryInsightsAnalyzer.swift`): local task history plus "Learned Preferences" auto-analysis. `HistoryStore` is a plain **JSON file** (`history.json`, 100-entry cap); `AgentMemoryStore` is the SQLite-backed store (task records, recomputed "Learned Preferences" every 100 recorded tasks). **The read side is gone rather than inert (2026-08-14 batch, P1-7):** the layer that had zero production callers — `entriesForPrompt`/`memoriesForPrompt`/`profileContextForPrompt`, all of `LocalMemoryRetriever.swift` (retriever + `LocalMemoryEmbedding` + `IndexedMemoryEvent`), and with them the `memory_embeddings` table and the NLEmbedding vector every recorded event used to be indexed into — was deleted. The product decision §11 asked for went the delete way: the sidecar's own store (below) is the one that actually reaches a prompt, and keeping a second, unwired one only made the next reader adjudicate it again. Nothing here is injected into Agent context, and the `/agent/run` body remains just `task + selectedText + conversationId` — the old "~12 most recent tasks budget injected into Agent-mode context" claim was never true in the wired code. `AgentMemoryStore` itself stays: task history, the "Learned Preferences" recompute, legacy-data sanitisation and history reset are all live. The "About Me" profile is still effectively dead data — its Settings editor was removed, so it is neither user-fillable nor injected (`ownerProfile`/`updateOwnerProfile` survive only for legacy-data sanitization; see §7).
- **Sidecar-side** (`sidecar/src/memory/`): a separate SQLite entity dictionary + free-text `owner_facts` (`MemoryStore.ts`) built from episodic events, with a consolidation ("dreaming") pass (`consolidator.ts`) that proposes/accepts canonical terms + aliases. **Consolidation now runs on its own (2026-08-14 batch, P1-7):** `memory/startupConsolidation.ts` consults the `shouldConsolidate` gate (≥12h since last run + ≥5 **eligible** unconsolidated events — see the transcribe exclusion below) once per launch, `STARTUP_CONSOLIDATION_DELAY_MS` (5 min) after the sidecar starts serving — one check, not a polling timer, guarded so two passes can never overlap, and swallowing any failure so a launch-time nicety can't take the sidecar down. `main()` holds only the one-line call; the decision lives in a testable seam, the same split `lifecycle.ts` uses. The manual triggers (`POST /memory/consolidate-now`, the `consolidate_memory_now` agent tool) still bypass the gate entirely. **All three modes now feed the episodic layer** (same batch): `/asr/transcribe` records `mode: "transcribe"` with the pre-correction ASR text as `rawTranscript` and the alias-corrected text as `correctedTranscript` — the one place in the product where a real mis-hearing/correction pair exists for free — and `/oneshot/ask` records `mode: "ask"` with `origin: "agent"` (its `result` is machine-produced text that may quote fetched web pages, so it must not enter consolidation labelled as the owner's own words). Both are best-effort and never fail their request; transcribe additionally skips empty/whitespace-only transcripts, so five accidental hotkey presses can't open the gate on nothing. `applicationName` is a placeholder (`"OpenType Transcribe"`/`"OpenType Ask"`, following `/agent/run`'s equally synthetic `"OpenType Agent"`) — the sidecar cannot know the frontmost app, and no wire-format change was made for it because `applicationName` never reaches the consolidation prompt. Managed from the macOS Settings "Memory" panel: since the 2026-08-14 batch (P0-4) the entity dictionary there is **editable, not read-only** — add (`POST /memory/terms`), inline edit (`PUT /memory/terms/:id`) and delete (`DELETE /memory/terms/:id`), alongside the owner-facts list (`GET`/`DELETE /memory/owner-facts`, the latter finally wired to a button) and the still-read-only run log (`/memory/consolidation-runs`). Every row renders its `origin` badge, since surfacing `untrusted` provenance is the point of P1-12's flag. Deletes are irreversible and confirmed with a dialog; there is still **no rollback UI** for a whole consolidation run (§11).

  **`origin` is promoted one way** (2026-08-14 batch): `upsertEntityTerm` — the single shared merge path — raises a merged row to `"owner"` when the incoming write is an owner write, and never downgrades an existing `"owner"`. The two owner writes are the panel's `POST /memory/terms` and P0-2's voice correction (`POST /transcribe/correct`); `remember_fact` (`"untrusted"`) and the dreaming pass (`"system"`) leave provenance alone. Without this, a term the owner personally vouched for would stay flagged untrusted forever, and a badge that survives review is noise users learn to ignore. Note the asymmetry: `PUT /memory/terms/:id` is a plain field patch and does **not** promote — editing an untrusted term in place leaves it untrusted.

Three routes now read this store, not two. `/asr/transcribe` reads `entity_terms` on every request to bias and correct recognition (§4's P0-1 note) — the dictionary's first non-LLM consumer, and the one that makes teaching a term visibly worth doing. The other two are the LLM paths described next; note that the ASR path deliberately filters by **confidence only, never by origin**, unlike the prompt paths below. That is not an oversight: `origin: "untrusted"` exists to gate what can reach an *instruction* channel, and biasing a decoder toward a spelling is a correction, not an instruction. Filtering ASR by origin would silently break the main way a user teaches OpenType a name, since `remember_fact` is one of the paths that writes them.

`/oneshot/ask` and `/agent/run` both pull a light memory context from the sidecar-side store (`sidecar/src/oneshot/memoryContext.ts`) before calling the LLM: a "Known terms: ..." line for entity terms *mentioned in this input*, **plus a "What you know about the user: ..." line carrying every `owner_facts` row of origin `"owner"`, injected unconditionally (not relevance-filtered)** — origin-gated by the P1-12 fix so untrusted/agent/system-origin facts are excluded, but all owner-authored facts are still included every time. This is not the fuller structured memory-profile prompt the old Swift-native `PromptBuilder` used to assemble (that file no longer exists). Each such call also appends a line to a local `context-debug.log` (`contextDebugLog.ts`, path via `OPENTYPE_CONTEXT_LOG_PATH`) recording the truncated (~200-char) input text and what context was matched — a persistent local record of ask/agent input not covered by the "reset input history" action. A third, separate table pair (`conversations`/`conversation_messages`, `sidecar/src/memory/conversations.ts`) holds Q&A/Agent multi-turn conversation history — see §9; it shares the same sqlite file as the entity dictionary but is conceptually distinct from both memory systems above (it's turn-by-turn chat history, not a fact/term store).

**Where the floating panels open, and what the listening pill shows (P2-10, 2026-08-14).** Two things changed about the HUD, both driven by the same batch item:

- **The panels follow the pointer, not `NSScreen.main`.** `OverlayController.visibleFrame()` and `ReviewPanelController.position(_:)` both used to read `NSScreen.main ?? NSScreen.screens.first`. `NSScreen.main` is the screen holding the *key window*, which for a menubar accessory app is stale or wrong often enough (nothing key, a full-screen space, a display back from sleep) that on a multi-monitor desk the HUD regularly opened on the display the user was not looking at. Hit-testing uses `frame` and the returned rect is `visibleFrame`: a pointer parked in the menu bar or over the Dock is still on that screen, but a panel is still laid out inside the usable area. It is read fresh on every presentation, never cached, so an open panel follows the user to another display and an unplugged one corrects itself. The bottom-centre/centre frame math is unchanged given a screen (`VoiceSurfacePanelLayout`, and Review's centring now extracted into `ReviewPanelLayout` for the same reason: 「Review 面板同理」 needed a seam that could go red).
- **The listening pill shows elapsed time, warns at 2 minutes, and stops itself at 5.** `AppModel` runs a half-second tick for exactly as long as a recording lasts (started/stopped off the one `setState` transition every recording path goes through, so no exit can leave a timer running). Each tick renders `RecordingClock.elapsedText(seconds:)` — `m:ss`, truncating, clamped at zero — into the pill's header, and asks `RecordingLimits.action(elapsed:alreadyWarned:hotKeyHeld:)` what this instant means. At 120s it fires one visual warning (the sentence takes the pill's caption line for 4.5s; the elapsed readout stays tinted afterwards). At 300s it **finishes and delivers**: `finishRecordingAtDurationLimit()` stops the clock and calls `hotKeyReleased()`, the exact path letting go of the hotkey takes — pointedly *not* `cancel()`/`cancelActiveVoiceSession()`, which call `audioRecorder.cancel()` and delete the file. That distinction is the whole point of the item (「5 分钟自动停止并正常交付，不是丢弃」) and is why `RecordingLimits.Termination` is a two-case enum with an unreachable `.discard`: choosing `.finishAndDeliver` is on the record. `hotKeyHeld` is passed to the policy and required to make no difference — a stuck modifier is indistinguishable from a held one here, and is exactly the case the cap exists for.

## 8. Direct vs. Tidy vs. Review transcribe mode

`transcribe` mode now has three variants, chosen by a persistent Settings toggle (`AppConfiguration.transcribeVariant`, `TranscribeVariant` in `Models.swift`, Settings' "转写" section) that applies to every `transcribe`-mode recording until changed — not a per-recording choice:

- **Direct** (default): hotkey → speech → the transcript is delivered immediately via the existing pipeline (clipboard + optional auto-insert). The delivery itself is still exactly the pre-existing `.transcribe` code path, with no added latency — but since the 2026-08-14 batch's **P0-3** it is followed by an 8-second correction window in which the hotkey offers to fix what was just delivered, in place. See "Direct's own correction affordance" below.
- **Tidy** (added by the 2026-08-14 batch's **P1-8**): identical to Direct except that the transcript passes through `TidyTranscript.tidy(_:)` first — filler removal (嗯/呃, 那个/就是说, um/uh/er), stutter collapsing, and punctuation/whitespace normalisation. **There is no LLM call, no sidecar call, and no provider requirement**: the rules are pure, synchronous Swift, so Tidy works with the network off and adds no measurable latency. That is the product promise, not an implementation detail — it is the tier between 「一字不改」 and 「问答」 for users who want cleaner text without their dictation reaching a model, and it is why "just ask the LLM to clean it up" is *not* an acceptable future refactor of this variant. Delivery, clipboard behaviour, and the P0-3 correction window are Direct's, unchanged.
- **Review**: hotkey → speech → the transcript is stashed in a floating, editable Review panel (`ReviewPanelController.swift`) instead of being delivered anywhere. Nothing is inserted or copied until the user explicitly commits.

### How the variant axis routes (P1-8)

`TranscribeVariant.deliverableText(for:)` is the single decision point: Direct returns the transcript, Tidy returns `TidyTranscript.tidy(transcript)`, Review returns `nil` meaning "staged, don't deliver yet" — the same "dispatched, don't wait" early-return path `.agent` uses. `AppModel.process(audioURL:)`'s `.transcribe` branch consults it and holds no opinion of its own about variants. Its companion `deliversIntoTargetApp` (true for Direct and Tidy, false for Review) is what the P0-3 correction window gates on, in both `CorrectionWindow.intent(...)` and `CorrectionWindow.reduce(...)`.

Tidy gets the correction window for a sharper reason than "it also delivers": it is the only variant whose output differs from what the user said, so a wrong word there can be OpenType's doing rather than only the recogniser's. Review stays excluded because its open panel already gives the second hotkey press a meaning.

**Audit**: a Tidy delivery writes the same event shape as any other — `rawTranscript` = what ASR heard, `effectiveInput` = what the user said after mode-routing, and the `.completed` event's `result` = the tidied text that was actually pasted. The cleaned form never overwrites `effectiveInput`, so both halves stay recoverable from the chain and the `.completed` event cannot contradict the `.recognized` event written earlier under the same `requestId`. `provider`/`model` stay `nil`, which for Tidy states that no model was involved rather than merely that a field is missing.

`TidyTranscript`'s own rules are documented in the file, which is worth reading before changing any of them: several are deliberately narrower than the feature brief that motivated them (`like` is not removed at all; 那个/就是说 need both a clause-leading position *and* a following mark; a two-character Chinese stutter is left alone because reduplication is grammatical). The governing asymmetry is that leaving a filler in is a cosmetic miss while deleting a real word is silent data loss.

Four narrowings came out of the stage-4 review, each closing a case where a rule that reads correctly rule-by-rule deleted or corrupted a real word (pinned in `TidyTranscriptFalsePositiveTests.swift`):

- **A filler that is a whole sentence is the utterance, not a hesitation.** 嗯 alone is 「yes」 and 那个 alone is 「that one」, so 「他问我明天去不去。嗯。」 and 「你要哪个？那个。」 kept their answers instead of losing them. A hesitation is by definition followed by the thing being hesitated about *inside the same sentence*, so requiring a sentence boundary on both sides separates the two shapes without touching 「嗯，我觉得可以。」. The exemption reads the **original** left neighbour rather than the output built so far — inheriting the clause-leading rules' promotion would exempt the last filler of an all-filler utterance and break idempotence.
- **A dot needs evidence on its right, too.** The widening guard only looked left, so a Chinese filename stem read as "Han character, then a full stop": 「打开 报告.pdf」 delivered 「报告。pdf」. A dot followed by an ASCII word character is inside a token (extension, domain, version), never a clause end.
- **Han numerals are values, not stutters.** The ≥3 collapse is Han-only precisely because repeated digits are a value, and Whisper writes a dictated 「二二二」 in Han as readily as in Arabic — 「我的房间是二二二号」 became 「二号」.
- **English repeats on purpose too.** The CJK side protected 哈哈哈 while "ha ha ha" collapsed to "ha" and "bye bye" to "bye"; the allowlist now exists on both sides.

### Why a Settings toggle, not a new `InputMode`

Review is a delivery-timing variant of `transcribe` (same ASR, same "preserve verbatim" semantics, same no-LLM character), not a new mode with its own prompt/behavior contract — so it's a second axis (`TranscribeVariant`) crossed with the existing mode enum, not a 4th `InputMode` case. Tidy joins the same axis on the same grounds: it changes how much deterministic local processing happens before delivery, and *not* whether a model sees the text, so it needs no prompt, no provider, and no mode of its own. This keeps `InputMode.visibleModes` (and everything keyed off it — the mode-cycle hotkey chord, `VoiceModeRouter`, the menubar `ModeGrid`) unchanged.

A per-invocation trigger (e.g. a hotkey chord meaning "this one recording, review it") was considered and deliberately not added: `GlobalHotKey`'s existing chord surface (hold/double-tap presets, plus recording-modifier+Tab to cycle mode — §1; the Option+Shift half of that chord was removed on 2026-08-14) is already dense, and every remaining unclaimed combination would either conflict with a preset or need its own discoverability affordance. The Settings toggle is simple, discoverable, and — per the task brief — required to work standalone regardless, so it was built as the only mechanism rather than half-building a second one.

### The correction flow, end to end

1. **Original dictation** (Review variant active): `AppModel.process(audioURL:)`'s `.transcribe` branch transcribes as normal, appends the usual `.recognized` audit event, then calls `beginReviewSession(...)` instead of delivering — this shows the panel (`reviewPanelState`) and records session bookkeeping (`ReviewSession`: `requestId`, the originally-captured `CapturedContext`, and the last audit event id for chaining). The panel is an `NSPanel` with `.nonactivatingPanel` + a `canBecomeKey` override — the same pattern `OverlayController` already establishes — so the app that was focused when dictation started stays frontmost the whole time the panel is open.
2. **Editing**: the panel wraps a real `NSTextView` (`ReviewTextView`, an `NSViewRepresentable` — SwiftUI's `TextEditor` selection-binding API needs macOS 14 and this app targets macOS 13) rather than mirroring text through `@Published` SwiftUI state on every keystroke. The user can type directly; the text view is the sole source of truth for "current text" once shown.
3. **Voice correction**: with the panel open, a second hotkey press means "correction for the panel's current selection," not "start a new dictation" — `AppModel.hotKeyPressed()` checks `reviewPanelState != nil` first and, if the panel has no text selected, gives immediate feedback (no wasted recording) rather than proceeding. Selection existence is checked *before* recording starts; the recording itself only captures the spoken instruction (ASR only — no `VoiceModeRouter`/mode-switch parsing applies to a correction recording). `processCorrection(audioURL:)` then calls the sidecar's new `POST /transcribe/correct` with the panel's full current text, the selection as a UTF-16 offset range, and the transcribed instruction; the response's `replacement` is spliced back into the `NSTextView` at the same offsets (`ReviewPanelController.applyCorrection`, via `TextSpanCorrection`) and the new span is re-selected so a follow-up correction can immediately target it again. Selecting the entire text and speaking a rewrite instruction (e.g. "rewrite this more formally") uses the identical mechanism with no special-casing — the endpoint doesn't distinguish "small span" from "whole text."
4. **Commit** (Enter button / **Cmd+Return**, not bare Return — see below) or **Cancel** (Escape / Cancel button / click outside the panel): commit inserts the panel's current text via the same `ContextBridge.insert(...)` Direct mode uses (always copies to clipboard too), records a `HistoryEntry`, and appends the session's final `.completed` audit event; cancel discards everything and appends a `.cancelled` event with no result.

**Why Cmd+Return, not bare Enter, for commit**: the panel is a real editable multi-line text view, where bare Return is expected to insert a newline (the user may want a multi-line corrected result). Overloading bare Return as "commit" would make it impossible to type a newline. Cmd+Return is the standard macOS resolution for exactly this conflict (Mail/Slack-style compose-and-send) and is shown next to a visible "写入 (⌘↩)" button; Escape is unambiguous (text views don't use it for anything) and is bound directly, both as a button and via `.onExitCommand`. This is a deliberate refinement of the task brief's "Enter to commit" framing, not a literal implementation of it.

### Audit chain, not a single event

Per session, `ImmutableAuditStore` now records more than one linked event, all sharing one `requestId` and chained via the (previously-scaffolded-but-unused) `supersedesEventId` field rather than a parallel logging structure:

- `.recognized` — the original dictation (already existed; reused as the chain's first link).
- `.corrected` (new `AuditEventStatus` case) — one per correction round. `rawTranscript` = the spoken instruction, `selectedContext` = the substring that was replaced, `effectiveInput` = the model's replacement, `result` = the full text after splicing — all existing fields, repurposed for this event kind rather than new ones being added.
- `.completed` (commit) or `.cancelled` (discard) — the session's final outcome, `supersedesEventId` pointing at the last correction (or the original `.recognized` event if there were no corrections).

A reader can replay the whole session — original text, every correction instruction and its result, and the final outcome — by following `supersedesEventId` from the terminal event backward, not just see the last state.

### Direct's own correction affordance: the post-delivery window (P0-3)

Review made corrections possible but charged for them up front — every dictation goes through a panel, whether it needed fixing or not. P0-3 (`docs/superpowers/specs/2026-08-14-product-batch-plan.md`) turns that from a global switch into an *afterwards*: Direct still delivers instantly, and for **8 seconds** after a delivery the hotkey changes meaning. If the target app has text selected at press time, pressing the hotkey means "voice-correct this selection" instead of "start a new recording."

- **In place, not back through a panel.** The first design re-opened the Review panel prefilled with the delivered text; that is wrong, because the text is already pasted into the target app — committing the panel would insert a second copy, and undoing the first paste with Cmd+Z is unsafe once the user has touched the keyboard at all in those seconds. `ContextBridge.capture()` already reads the selection and `ContextBridge.insert()` is Cmd+V, which natively *replaces* one, so in-place correction needs no undo, no panel, and no new write path. It also works on text OpenType never produced.
- **The decision is a pure seam.** `CorrectionWindow.swift` — `intent(...)` returns `HotKeyIntent.correctSelection`/`.startNewRecording`, and `reduce(_:on:)` moves a `CorrectionWindow.State` over `delivered`/`correctionSucceeded`/`correctionFailed`/`recordingStarted`/`cancelled`. The window is the half-open interval `[delivery, delivery + 8)`, so expiry needs no timer: a stale window behaves exactly like none. App identity is delegated to `OutputDeliveryPolicy.shouldInsert` rather than re-derived, since a correction writes through the very same insert path a delivery does and the two must not disagree.
- **It never steals the hotkey.** Window hot but nothing selected → ordinary new recording. Someone who wants to correct selects first; someone who just wants to say the next sentence must not be interrupted.
- **Delivering transcribe variants only** (Direct and, since P1-8, Tidy). Ask/Agent cards already give a second utterance the meaning "continue this conversation" (`VoiceFollowUp`), and Review's open panel already owns the hotkey. Both halves are enforced: `reduce` refuses to arm unless the delivery was `transcribe` + `variant.deliversIntoTargetApp` (and an ineligible delivery *closes* an open window), and `intent` re-checks the mode the user is in **now** — the two together are what stop a window armed in one mode from being spent in another. The gate asks `TranscribeVariant.deliversIntoTargetApp` rather than listing cases, so a fourth variant has to state whether it delivers instead of inheriting an answer.
- **`AppModel.hotKeyPressed()` decision order**: Review panel open → the existing panel-correction path, unchanged; else `CorrectionWindow.intent(...)` says `.correctSelection` → `beginInPlaceCorrectionRecording`; else → new recording, unchanged. The correction round records the instruction only (ASR, never `VoiceModeRouter`), sends the selection as `fullText` with the span `0..<utf16.count` to the same `POST /transcribe/correct`, pastes the `replacement` back over the selection, and copies to the clipboard per the always-copy invariant. Both correction paths share one `requestCorrection(fullText:range:instruction:)` helper.
- **The paste is re-checked at write time, not only at press time.** The selection is read when the hotkey is pressed, but the paste lands an ASR + `/transcribe/correct` round trip later — and `insert` is Cmd+V, which replaces whatever is selected *then*. So `processInPlaceCorrection` re-reads the target immediately before writing and refuses the paste unless the frontmost app still passes `OutputDeliveryPolicy.shouldInsert` **and** the live selection is still byte-identical to the one that was corrected; otherwise it downgrades to clipboard-only with a `lastDeliveryNotice` saying why. This is a strictly stronger guard than the delivery path's, which only re-checks the app: dictated text landing in the wrong window is bad, but a replacement derived from one span pasted over a *different* span destroys text the user never pointed at.
- **Audit**: one `.corrected` event per round, `supersedesEventId` pointing at that delivery's `.completed` event (or the previous round's `.corrected`) — the same chain shape Review uses, so a Direct correction is a link in the delivery's chain rather than an orphan. `AppModel` keeps those anchors in `CorrectionWindowSession` alongside the pure window state.
- **Lifecycle**: cleared on a new recording (`beginRecording`, the one choke point — deliberately *not* `beginCorrectionRecording`, whose round has to survive long enough to re-arm), on Esc, and by expiry; **re-armed with a fresh 8s** on a successful correction, because fixing two words in a row is common. A *failed* correction neither re-arms nor clears: the window keeps running on its original clock.
- **Visibility is the feature, not decoration.** 「用户看不见这个窗口，这个功能就等于不存在」. `OverlayHideBehavior` gained `.scheduleHideWithCorrectionHint(after:)` and `OverlayController.hideBehavior(for:correctionWindowArmed:)`; while a window is open, the `.success`/`.copied` toast stays up for the window's full duration (not 0.9s), carries `CorrectionWindow.hintText`, and runs a bar that empties exactly as the window does. The duration comes from `CorrectionWindow.windowSeconds` itself so the bar cannot promise time the hotkey will not honor. `AppModel` keeps `overlay.correctionWindowArmed` in step with the window through one setter (`syncCorrectionWindowAffordance`), and `scheduleIdle` takes a matching longer delay so the model's state does not fall back to idle and tear the hint down early.
- **The trap the compiler does not catch**: `OverlayHideBehavior` has two consumers in `OverlayController`. `presentLegacy`'s exhaustive `switch` fails to build if a new case is unhandled; `presentToast`'s `guard ... case .scheduleHide(let seconds)` does **not** — an unhandled case there compiles fine and silently stops the preempted unified voice surface from ever being restored. Both now read the delay from one `OverlayHideBehavior.scheduledHideDelay` accessor instead of matching a single case, so the next case added cannot reintroduce this.
- **Closes the loop with P0-2**: this path is the same `/transcribe/correct`, so a correction made in the user's own text field also teaches the entity dictionary — fix a term once, and the next transcription gets it right. Its `learned` field is decoded Swift-side but not yet surfaced; the 「已记住」 affordance is separate work.

### Sidecar: `POST /transcribe/correct`

New endpoint, `sidecar/src/transcribe/{routes,prompts}.ts`, TDD'd (`sidecar/test/transcribe/correct.test.ts`, 8 tests, confirmed red — `Cannot find module` — before implementation, green after). Takes `{ fullText, selectionStart, selectionEnd, instruction }` (offsets, not the selected substring alone, per the task brief's own reasoning: unambiguous even when the target phrase repeats elsewhere in the text) and returns `{ replacement }` — the caller splices it back in, the endpoint never sees or returns the rest of the document. Takes a bare `chat` function (same DI shape as `buildOneShotRoutes`); validates the selection range (400 on `start >= end`, out-of-bounds, or a blank instruction) before ever calling the LLM.

The endpoint originally had **no** `MemoryStore`/entity-dictionary dependency at all, deliberately, and was described here as pure dependency-light logic. The 2026-08-14 batch's **P0-2** broke that on purpose — a correction the user made by hand is the single best signal for what the dictionary should contain, and leaving it unrecorded meant the user re-corrected the same word forever. The store is now an **optional** second argument (`buildTranscribeRoutes(chat, deps?)`): omitted, behavior is byte-for-byte what it was, which is still how most of `correct.test.ts` exercises it; supplied (as `server.ts` does), a correction that passes the gate in `learnCorrection.ts` is also written to `entity_terms` as `alias → canonicalTerm` via the shared `upsertEntityTerm` merge path, at `category: "term"`, `confidence: 0.8`, `origin: "owner"`, and echoed back as `learned` for the UI.

That gate exists because `/transcribe/correct` serves two unrelated jobs with an identical request shape: fixing a mis-transcribed *term* ("呸泡" → "PayPal"), which is exactly what the dictionary wants, and rewriting a span of prose ("rewrite this more formally"), which would poison it. `shouldLearnCorrection` decides between them after the fact from the two strings alone — both sides non-empty and differing case-insensitively, both ≤ 24 UTF-16 code units, no newline in the replacement, the replacement not containing the selection (an expansion, not an alias), neither side pure punctuation/whitespace. It is a pure function, and conservative on purpose: a false negative costs one repeated correction, a false positive silently rewrites every future transcript. Learning is strictly **best-effort** — it runs after the correction has already succeeded, and every store touch is inside one `try`, so a corrupt or unwritable memory DB degrades to "learned nothing", never to a failed correction.

Offsets are UTF-16 code units on both ends of the wire — `NSTextView.selectedRange()`/`NSRange`/`NSString` on the Swift side and native JS string indexing (`.slice`) on the sidecar side use the exact same representation, so raw integers pass through with no re-encoding step that could introduce an off-by-N bug for text outside the Basic Multilingual Plane. `TextSpanCorrection.swift` (Swift) documents and unit-tests this; a sidecar test (`"uses UTF-16 code unit offsets..."`) checks the same contract from the other end.

### What was drawn from OpenTypeless, and what wasn't

Per `docs/references/opentypeless-stt.md`: OpenTypeless has no panel-based review/stash step and no voice-scoped span-correction endpoint — its closest analog is `SELECTED_TEXT_ADDON`, a prompt fragment appended when text is already selected in the *target app* at request time, always going through its single always-on "polish" LLM pass. Nothing here was ported directly. What *was* useful as a reference:

- The reference notes' framing of "faithful correction, not generative rewrite" as something OpenTypeless leaves to prompt wording alone, with no structural guard — this is exactly why `CORRECTION_SYSTEM_PROMPT` is scoped hard ("Return ONLY the replacement text for the selected span... Never change or repeat anything outside the selected span") and why the Swift side splices only the returned span back in by offset rather than trusting the model to return a whole corrected document — a structural guard OpenTypeless doesn't have anywhere in its pipeline.
- Confirms this feature is new ground, not an adaptation of existing prior art: OpenTypeless's own roadmap treats automatic/voice-driven personal-vocabulary correction as an unscheduled, unimplemented gap (see that doc's "Still a gap" section) — this feature's whole mechanism (select a span inside a *stashed, not-yet-delivered* result, speak a correction, splice in place) has no OpenTypeless equivalent to diverge from or borrow beyond the general "faithful, narrowly-scoped correction" principle above.

## 9. Conversation continuation (Q&A / Agent tabs)

Ask and Agent mode are one-shot by default (a fresh `/oneshot/ask` or `/agent/run` call with no history) but can continue a specific past exchange: the Q&A tab lists past Ask conversations (`GET /conversations?kind=ask`, most-recently-updated first); tapping one fetches its full thread (`GET /conversations/:id`) and marks it as `AppModel.focusedAskConversationId`. The next time Ask mode is dispatched by voice while that id is set, the request includes `conversationId`, and the sidecar replays the conversation's prior messages as real chat history (not a squashed context blob) before the new question — genuine multi-turn continuation, verified against a real DeepSeek call by asking a question that only resolves given the prior turn (e.g. "why do I like it?" after "my favorite language is Rust"). The Agent tab (`AppModel.focusedAgentConversationId`) works the same way, except prior turns are folded into the loop's `context` as a short "previous task / previous result" summary rather than a full message-array replay (Agent's loop message shape doesn't carry arbitrary history the same way).

Leaving the thread view or using the tab's "new conversation" affordance (`AppModel.startNewAskConversation()`/`startNewAgentConversation()`) clears the focused id, so the next dispatch starts fresh again. A tapped Agent-completion notification (`focusAgentRun(_:)`) now selects the Agent tab and opens that run's conversation thread directly, using the `conversationId` recorded onto its `AgentRunRecord` once the run completes (§3).

## 10. Provider configuration (Whisper local/remote, LLM Anthropic/OpenAI-compatible)

Added after this doc's original writing, deliberately reversing §5/§7's "no cloud-provider picker" state per explicit product direction. Full design:

**Whisper (ASR).** A Settings/onboarding choice between:
- `local` (default, unchanged) — the existing sidecar-managed MLX-Whisper process (§4).
- `remote` — implements OpenAI's audio transcription shape (`POST /audio/transcriptions`, `whisper-1`/`gpt-4o-transcribe`-family models), against a **user-supplied base URL**, not hardcoded to `api.openai.com` — so a self-hosted OpenAI-API-compatible transcription server works too. `sidecar/src/asr/remoteWhisperClient.ts`. This is an assumption worth revisiting if a different "remote Whisper" shape turns out to matter more in practice (e.g. a raw self-hosted `faster-whisper` server with a non-OpenAI-shaped API).

No live "remote Whisper" account was available to verify a *successful* remote transcription end-to-end — that gap is real, tracked below.

**LLM provider.** A Settings/onboarding choice between:
- **Anthropic** (Messages API shape, `/v1/messages`) — `sidecar/src/provider/anthropic.ts`. Translates both directions: OpenAI-shaped tool defs/tool_calls/tool-result messages (the shape `agent/loop.ts` and this codebase's other providers use) into Anthropic's `input_schema`/`tool_use`/`tool_result` content-block shape and back, so `/agent/run`'s tool-calling loop works unmodified regardless of which provider is active.
- **OpenAI-compatible** (Chat Completions shape, `/chat/completions`) — `sidecar/src/provider/openaiCompatible.ts`. Covers DeepSeek, OpenAI itself, and self-hosted servers sharing this shape; structurally the same request/response handling as the original `provider/deepseek.ts` (which is untouched and remains the zero-config fallback client, not superseded).

Both implement a shared `LLMProviderClient` interface (`chat`/`testConnection`/`listModels`, `sidecar/src/provider/types.ts`), dispatched by type via `sidecar/src/provider/registry.ts`. `testConnection()` prefers `GET /models` (cheap, no generation cost); if that 404s (some minimal self-hosted servers only implement chat), it falls back to a 1-message chat call so a real-but-listing-less server still reports success. `listModels()` throws on failure, and callers (`provider/routes.ts`'s `POST /config/llm/models`) catch that and substitute a hardcoded `KNOWN_MODELS_FALLBACK` list per provider type (current common OpenAI/DeepSeek and Anthropic model names as of this writing) rather than leaving the picker empty.

**Config storage.** `sidecar/src/provider/configStore.ts`'s `ProviderConfigStore` persists both configs as **plaintext JSON** next to the sidecar's existing SQLite data directory (same directory convention as `dbPath`/`whisperSocketPath`), `chmod 600`'d after every write. Deliberately *not* Keychain-backed — see that file's doc comment for the full reasoning, briefly: (a) the sidecar already stores other locally-sensitive data (the memory SQLite DB) unencrypted, so this doesn't lower the app's existing trust bar, and (b) Keychain-on-Swift-side would reintroduce the exact credential-plumbing-through-env-vars-at-spawn-time coupling this rewrite's earlier cleanup pass removed, and would need re-spawning the sidecar (or a live env-reload mechanism that doesn't exist) on every key change. `chmod 600` is the mitigation actually available at this layer; a real remaining gap if the local machine account itself isn't trusted.

**"Configured" is explicit, never ambient.** `ProviderConfigStore`'s `llmConfigured`/`whisperConfigured` booleans are only set by an actual `PUT /config/llm`/`PUT /config/whisper` call completing — i.e. the user finished Test Connection + model pick + Save (LLM) or explicitly chose a Whisper mode and saved (local or remote). An ambient `DEEPSEEK_API_KEY` env var alone never flips either flag. `GET /config/status`'s `ready = llmConfigured && whisperConfigured` is what gates the onboarding wizard.

**HTTP surface** (`sidecar/src/provider/routes.ts`, all consumed by `AppModel.swift`'s "Provider configuration" section, never by raw Swift-side Keychain/file access): `GET /config/status`, `GET`/`PUT /config/llm`, `POST /config/llm/test`, `POST /config/llm/models`, `GET`/`PUT /config/whisper`, `POST /config/whisper/test`. Responses never echo a raw API key back — only a masked preview (`apiKeyMasked`, e.g. `sk-b...81ff`).

**Onboarding wizard.** `Sources/OpenType/ProviderSetupViews.swift`'s `OnboardingWizardView` replaces `RootView`'s normal tab content (Home et al.) whenever `AppModel.needsProviderOnboarding` (derived from `providerConfigStatus.ready`) is true, and disappears automatically the instant both are saved (no separate "Finish" action needed — saving refreshes `providerConfigStatus` reactively). The app auto-opens the real main window the first time a launch discovers onboarding is needed (`AppModel.init`'s post-sidecar-ready check, guarded to fire once per launch), since the wizard lives in that window alongside Settings, not in the compact menubar popover. It reuses `WhisperSetupContent`/`LLMProviderSetupContent` verbatim from Settings' "语音识别"/"AI 模型" sections — one implementation, not a parallel wizard-only copy.
