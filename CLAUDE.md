# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

OpenType is a local-first, macOS-only AI voice-input tool: it turns spontaneous speech into ready-to-use text. `Sources/OpenType` is the Swift shell (menubar app, hotkeys, Accessibility, delivery, local history/audit); `sidecar/` is the TypeScript/Bun child process it spawns and manages over a Unix socket, which owns every actual ASR/text-generation call plus the local memory/entity-dictionary store. See "Architecture (macOS reference implementation)" below for the full current shape.

OpenType previously had iOS and Android clients (`Platforms/iOS`, `Platforms/Android`) meant to share one cross-platform behavioral contract with macOS (`Shared/OpenTypeContract.json`, `Shared/Schemas/`, `Shared/AcceptanceCases.json`, `docs/MULTIPLATFORM_ARCHITECTURE.md`) — same modes, same prompt/safety rules, same provider semantics, same audit protocol. That contract went stale once macOS went through its from-zero rewrite (old 5/6-mode system → exactly 3 modes, plus a sidecar-owned memory/LLM/agent layer) without iOS/Android following along, and rather than doing the deferred reconciliation work, the product decision was to **remove iOS, Android, and the shared contract entirely** — they are gone from this repo, not just stale. If you find an old commit, spec, or external reference mentioning them, treat it as history, not as describing current repo contents.

## Development workflow

This repo is mid-rewrite. The new product design (comprehensive local memory/context management, a unified voice-triggered Agent entry point with a product-owned Agent runtime, context-aware speech-to-text correction — see `docs/references/` and `docs/superpowers/specs/`) differs enough from the current MVP that the existing code should be treated as prior art to consult, not as a constraint on the new design.

> **Fix batch (branch `fix/review-2026-08-10`):** a large review-driven batch landed here in response to `docs/reviews/2026-08-10-comprehensive-review-for-opus.md` — all P0s, all P1s, and many P2s (transport hardening, sidecar supervision/single-instance guard, cancellation, Review-panel second-session fix, memory-poisoning close, error envelopes, unbundled dev key, etc.). Some behavior in older docs predates it; the docs listed below have been reconciled to this branch's code. Still-open items are tracked in current-state §11.

All feature implementation follows a strict TDD red/green cycle, run as an explicit 4-stage pipeline across separate agents rather than one agent doing everything end to end:

1. **Write tests** — one agent writes the test(s) for the behavior, nothing else.
2. **Review tests** — a separate agent reviews the tests for correctness and confirms they currently fail (red) for the right reason.
3. **Implement** — a separate agent writes the implementation to make the reviewed tests pass, without weakening or rewriting them.
4. **Review implementation** — a separate agent reviews the implementation. If it passes, commit immediately — auto-commit is pre-authorized specifically for this 4-stage pipeline once all stages pass; no need to check back in per change.

Dispatch each stage manually (one Agent tool call per stage) rather than via a saved Workflow script for now — revisit automating the whole pipeline once its shape feels stable.

**Who runs which stage is not negotiable (owner rule, 2026-08-15):**

- **All development work goes to sub-agents, and those sub-agents run on Sonnet** (`model: "sonnet"` on the Agent call). That covers writing tests, writing implementations, and the mechanical parts of a fix.
- **The main agent stays on Opus and does not write feature code itself.** Its job is orchestration and review: decomposing the batch, deciding what each stage must prove, reading the diffs, adjudicating design questions the sub-agents surface, and committing.

The reason the split is worth stating: the expensive judgement in this pipeline is deciding *what is correct* — which test would actually catch the bug, whether a green suite proves the thing it claims, whether a doc that says "not fixed" still matches the code. That judgement is the main agent's whole contribution, and it is wasted if the main agent is also burning its turn on mechanical edits. If the main agent starts implementing, it is doing the cheap half of the work with the expensive model and reviewing its own output, which is exactly the loop this project's 4-stage split exists to break.

Treat this project's own documentation (`docs/`) as equally important as the code it describes: update the relevant spec/reference doc as part of finishing a piece of work, not as a follow-up. `docs/references/` is the entry point for OpenTypeless/OpenClaw research (read it before re-exploring either repo from scratch); `docs/superpowers/specs/` holds the dated design specs this rewrite produces.

## Commands

### macOS (SwiftPM)

```bash
swift build                                   # debug build
swift test                                    # run all tests
swift test --filter <TestClassOrMethodName>   # run a single test
./scripts/build-app.sh                        # release build -> dist/OpenType.app, ad-hoc codesigned
open dist/OpenType.app
```

`scripts/build-app.sh` builds release, compiles the `sidecar/` TypeScript/Bun server into a standalone `opentype-sidecar` binary (requires `bun` on PATH), assembles the `.app` bundle (binary, Info.plist, Sounds, en.lproj, the bundled sidecar binary, the bundled MLX-Whisper Python venv + script, the bundled `sidecar/skills/` and `sidecar/agents/` built-in roots — without these a packaged binary's `import.meta.dir`-relative default resolves into its own embedded virtual filesystem rather than a real directory, so `SidecarClient.bundledSkillsAndAgentsEnvironment` points `OPENTYPE_SKILLS_DIR`/`OPENTYPE_AGENTS_DIR` at these bundled copies instead, packaged launches only), strips quarantine, and codesigns the sidecar binary standalone *before* folding it into the app (a `bun build --compile` binary's non-standard Mach-O format breaks under `codesign --deep` on the outer app — sign inner-then-outer, outer without `--deep`), then codesigns the outer `.app`. Two signing paths: by default an **ad-hoc** sign with a stable designated requirement (`identifier "ai.rain.opentype"`) so TCC permissions (mic/Accessibility) survive rebuilds; setting `OPENTYPE_NOTARIZE=1` instead does an opt-in **Developer ID** sign (each nested Mach-O individually, `--options runtime --timestamp`) plus `xcrun notarytool submit`/`stapler staple` for a Gatekeeper-clean distributable (needs a Developer ID Application cert + notarytool credentials — either App Store Connect API key or a stored `store-credentials` profile).

By default the build **no longer bundles the developer's `sidecar/.env.local`** (which holds real secrets like `DEEPSEEK_API_KEY`) into the app — pass `--bundle-env` to opt into folding it in as `Contents/Resources/sidecar.env` for a private, non-distributed local build only (it prints a "DO NOT distribute" warning). A distributable build ships with no API key; the user configures a provider via the onboarding wizard/Settings.

### macOS sidecar (TypeScript/Bun, `sidecar/`)

```bash
cd sidecar
bun install
bun test                  # run all sidecar tests
bun run src/server.ts     # run standalone (dev mode), listens on a Unix socket
bun run build              # -> dist/opentype-sidecar, the standalone binary build-app.sh bundles
```

See `sidecar/README.md` for env vars (`DEEPSEEK_API_KEY` etc.), endpoint list, and directory layout. The Swift app spawns this as a child process (`Sources/OpenType/SidecarClient.swift`) rather than talking to any of the old cloud speech/text providers directly.

## Architecture

macOS is a **Swift shell + TypeScript sidecar** split, not a pure Swift app. `Sources/OpenType/AppModel.swift` is still the central `@MainActor` orchestrator (`ObservableObject`) every view binds to, but it no longer talks to any cloud speech/text provider directly — the Swift side owns recording, hotkeys, Accessibility, delivery, and local history/memory bookkeeping, and hands every actual ASR/text-generation call off to a local `sidecar/` (TypeScript/Bun) child process it spawns and manages over a Unix socket. See `sidecar/README.md` for the sidecar's own layout and standalone run/test instructions, and `docs/superpowers/specs/2026-08-09-current-system-state.md` for the full as-built reference (endpoints, request/response shapes, known gaps).

**The pipeline**: capture context → record → ASR (sidecar `/asr/transcribe`; local MLX-Whisper by default, or a user-configured remote provider — see "Provider configuration" below) → route by mode → (for `ask`/`agent`) sidecar text generation (DeepSeek by default, or a user-configured Anthropic/OpenAI-compatible provider) → deliver result (clipboard always; auto-insert into the focused field when enabled).

Since the 2026-08-14 product batch (`docs/superpowers/specs/2026-08-14-product-batch-plan.md`), the ASR step is **no longer dictionary-blind**: `/asr/transcribe` reads the sidecar's entity dictionary on every request and applies it twice — a `initial_prompt` decoding bias on the way in (local MLX-Whisper only; the remote OpenAI-shaped API has no equivalent) and a deterministic alias → canonical rewrite on the way out (both backends). `sidecar/src/asr/dictionaryBias.ts`. This is the first non-LLM consumer of the memory store, and it is what makes `transcribe` mode — the one mode that never calls a model — still get better the more you use the product.

Since the 2026-08-15 batch (§C), the same request also carries the user's **speech-recognition language** setting: `AppModel.transcribeRequestBody` puts `TranscriptionLanguage.whisperCode` (ISO-639-1 — a different vocabulary from the `appleLocaleIdentifier` the live-caption preview uses, and not derivable from it) on the body, and both backends honour it. `automatic` sends **no `language` key at all**, so the default request is byte-for-byte the one that predates the field. Before this the picker's 27 languages reached only the Apple preview, which is the false promise `docs/reviews/2026-08-15-product-review.md` §2 describes.

**The 3 modes** (`InputMode` in `Models.swift`) — down from an original 6-mode set, cut in two rounds tonight (6→5, then 5→3):

- `transcribe` — no sidecar/LLM call at all, in any variant: what MLX-Whisper hears is the result. Has three delivery variants (`TranscribeVariant`, a Settings toggle, not a 4th `InputMode`): `direct` (deliver the transcript immediately and verbatim, the original behavior), `tidy` (added by P1-8 — run the transcript through `TidyTranscript.swift` first, then deliver exactly as `direct` does) or `review` (stash the transcript in a floating, editable panel — `ReviewPanelController.swift` — where a second hotkey press means "voice-correct the current selection" via the sidecar's `POST /transcribe/correct`, and commit is Cmd+Return, not bare Return, since the panel is a real editable text view). **`tidy` is deterministic local rules and must stay that way** — filler removal, stutter collapsing, punctuation/whitespace normalisation, all pure synchronous Swift with no provider call. It is not the deleted `polish` mode returning: "just send it to the model and clean it up" is the one refactor this variant exists to rule out, and `tidy`'s pure non-async signature is what enforces it. `TranscribeVariant.deliverableText(for:)` is the single routing seam (`nil` = staged, don't deliver), and `deliversIntoTargetApp` (true for `direct`/`tidy`) is what the P0-3 correction window gates on.
- `ask` — no selection needed; speaks a question, sidecar's `/oneshot/ask` answers it directly in the **unified voice surface**. Since the 2026-08-13 ask-web batch (`docs/superpowers/specs/2026-08-13-b2-open-file-and-ask-web-design.md`) Ask is **LLM + internet**: `/oneshot/ask` runs the same `runAgentLoop` the agent uses, but with a web-only toolset (`opentype__web_search` + `opentype__web_fetch`, narrowed via `filterToolSet`) and a 6-iteration cap. That toolset difference *is* the product line between the two modes — Ask can search and read the web, Agent gets everything. (We use our own web tools rather than a provider-native server-side search because DeepSeek, the zero-config default, has none.) The answer renders in the **unified voice surface** — — one bottom-center `NSPanel` (`OverlayController`) whose listening pill morphs into a Markdown result card (spec: `docs/superpowers/specs/2026-08-13-hud-morph-result-surface-design.md`). The separate center-screen `AskPanelController` popup and top-right `AgentProgressPanelController` are deleted; both lifecycles now run through `VoiceSurfaceState` (a pure reducer over mode + `ProcessingState` + `AskPanelState` + `AgentProgressPanelState`) driving that single panel. The one mode that answers rather than preserves/transforms the input.
- `agent` — speaks a task; dispatched non-blockingly to the sidecar's `/agent/run`, which runs a tool-calling loop and returns a result plus a step log. Since the 2026-08-13 core-tools batch (`docs/superpowers/specs/2026-08-13-b2-agent-core-tools-v2-design.md`) the agent has a real built-in toolset (`sidecar/src/agent/coreTools.ts`): `opentype__bash`, `opentype__python`, `opentype__read_file`, `opentype__list_dir`, `opentype__grep`, `opentype__web_search` (DuckDuckGo scrape), `opentype__web_fetch`, `opentype__open_file` (execs `/usr/bin/open` so the macOS default app previews or plays the file — this is how "找到那个文档打开预览一下" / "播放这段音频" work; we deliberately do not embed our own viewers) — plus the two memory tools and any user-configured MCP servers (`OPENTYPE_MCP_SERVERS` env var). Since the 2026-08-28 first-party-tools batch (`docs/superpowers/specs/2026-08-28-first-party-tools-skills-and-agents-design.md` §2) the toolset also has real write access, not just `bash` heredocs: `opentype__write_file`, `opentype__edit_file` (exact-string find/replace, refuses an ambiguous multi-match rather than guessing which one), `opentype__move_file` (the one hard refusal in the batch — never silently overwrites an existing destination file), `opentype__trash` (moves into `~/.Trash` with sequential ` 2`/` 3` collision suffixes rather than deleting — see the approval paragraph below for why), and `opentype__glob` (recursive filename search, default cap `GLOB_DEFAULT_LIMIT` = 200, skips `.git`/`node_modules`/`Library`/dot-directories). Default working directory is the user's home; the prompt tells it to check `~/Desktop` and `~/Downloads` first for unlocated files. **No sandbox (deliberate YOLO-mode owner decision)**, and — since that same 2026-08-28 batch's §2.1 loosened the default further — **no confirmation for destructive tool calls either**: the owner's stated stance is usability over safety ("先【好用】再考虑安全。否则根本没人用"), so `/agent/run`'s approval gate defaults to auto-allowing everything, including the destructive shell/python calls it used to stop for. Every call still flows through the `ApprovalPolicy` seam (`sidecar/src/agent/approval.ts`) via `withApproval`, and which policy `handleAgentRun` applies per run is now controlled by `env.agentApprovalMode` (`OPENTYPE_AGENT_APPROVAL`, resolved once in `server.ts` and threaded down through `buildApp` → `buildAgentRoutes`'s trailing `approvalMode` parameter): `"yolo"` (the default, and the only value an unrecognised env value falls back to) is `yoloApprovalPolicy`, always-allow; `"prompt"` restores the previous behavior — the P1-6 prompting policy built per run in `handleAgentRun` (it needs that run's id/signal/ask_user broker, so it cannot live at `server.ts`'s construction-time `withApproval`, which keeps the always-allow baseline for `/oneshot/ask` unconditionally). That prompting policy is unchanged and fully intact, not deleted: it asks `classifyCommandRisk` (`sidecar/src/agent/commandRisk.ts`) and only stops for **named** destructive shell/python operations — `rm`/`find -delete`, the overwriting family at head position, truncating `>`, `dd`/`mkfs`, `chmod -R`, `git push --force`/`reset --hard`/`clean -f`, `sudo`, `eval`/`trap`, a pipe into any interpreter that would run it (`curl | sh`, `curl | python3`), python's `shutil.rmtree`/`os.remove`/`subprocess.*`/`exec`/`eval`, plus any bash/python payload it cannot parse. It tokenises rather than pattern-matches, so subshells, `$(…)`, `bash -c`, here-strings, `$IFS` splitting and wrapper prefixes do not hide a name from it. General python file writes and all MCP tools are unclassified **on purpose** (unbounded write surface; no args grammar) — a guard that fires often is one the user learns to click through, which is worse than none. The five file tools above are unclassified too, on purpose, in either mode: `classifyCommandRisk` only ever special-cased `opentype__bash`/`opentype__python` by name, and giving the model a recoverable `trash` instead of `bash rm` is the point, not a gap to close. So the tokeniser narrows the blast radius of a misheard task; it was never a boundary, and demoting it to opt-in (942 lines, reachable in full behind one flipped env value) is a reversible loosening, not a deletion. Paired on the Swift side by a pre-dispatch confirmation (`Sources/OpenType/DispatchConfirmation.swift`): an agent task shows its transcript on the voice surface for 1.5s with Esc to cancel before `/agent/run` is called — not a modal, the default is proceed, and agent only (ask is draft-only and higher-frequency). The final *answer* is still draft-only (copied to clipboard, never auto-sent); the old "no-side-effect tools only" policy is retired. The same 2026-08-28 batch also adds **agent definitions** (design §4, `sidecar/src/agent/agentDefinitions.ts` + `sidecar/src/agent/agentRoots.ts`): a single Claude-Code-compatible subagent `.md` file (frontmatter `name`/`description`/optional `tools`/optional `model` — `model` is parsed but deliberately ignored, since this product has exactly one globally-configured LLM provider — plus a system-prompt body) that lets a spoken task be addressed to a named persona instead of the one generic agent. Discovery is three roots, first-root-wins, same shape as the skill subsystem above and built on the same shared `sidecar/src/resources/` discovery layer (`layout: "file"` instead of `"directory"`): built-in `sidecar/agents/` (`OPENTYPE_AGENTS_DIR`-overridable) → `~/.opentype/agents` → read-only Claude-Code-compat `~/.claude/agents`. Selection is voice-first: `resolveAgentFromTask` matches a leading `用<name>`/`使用<name>`/`让<name>`/`叫<name>`/`<name>，`/`@<name>` address (against the file's `name` or an optional `displayName` alias) and strips it before the rest reaches the model — a name merely mentioned mid-task, not leading it, never matches, since a false positive here silently swaps the user's whole system prompt. `POST /agent/run`'s optional `agentName` field is the same selection made explicit (an unrecognised name is a 400), and takes precedence over the voice match; `GET /agent/definitions` lists every discovered agent's name/description/source-root/tools. A selected agent's body is **appended** after the harness's own `AGENT_SYSTEM_PROMPT`, never substituted for it, so a user-authored `.md` file can never turn off that prompt's own UNTRUSTED-data defenses — and its `tools` allowlist (accepting our bare/prefixed names and Claude Code's capitalised ones interchangeably) narrows only the "hands and feet" tool set, applied before the always-present `ask_user` escape hatch is added in, never after. Separately, any root's `~/.opentype/INSTRUCTIONS.md` (renamed from `AGENTS.md`, see below) is owner-authored global instructions appended after the agent body (every root that has one, in root order, additive rather than first-root-wins) — but that lookup uses a **shorter**, different root list (`resolveGlobalInstructionRoots`: built-in + `~/.opentype` only) that deliberately **excludes** `~/.claude`: an imported skill or agent is opt-in (the model must name it before it matters), while this global-instructions file is unnamed and always-on, so including the compat root would silently inject the user's Claude-Code coding instructions into every voice-dictation task — same directory tree, two different consent models, drawn at "does it require being named."

  **Project `AGENTS.md` — the real agents.md standard (design §10, owner instruction 2026-08-28,** `sidecar/src/agent/projectAgentsMd.ts` + `projectContext.ts`**).** §4.5 above had borrowed the filename `AGENTS.md` for a user-global instructions file, which is not what https://agents.md/ actually is; the owner asked for the real standard once that collision was noticed, so the global-instructions file above was renamed to `INSTRUCTIONS.md` and `AGENTS.md` now means only this: a free-form markdown file at a **project's own root** (a monorepo may nest one per package) telling an agent that project's conventions. Per the standard: the **closest** `AGENTS.md` to where the agent is working wins outright — no merging with an ancestor's, ever. Two entry points, both required because "which project" is often discovered mid-task, not known at the start (a user says "看看这个项目的测试为什么挂了" starting from the home directory): (1) **run start** — `POST /agent/run`'s optional `workingDirectory` field (default `~`) walks upward once; (2) **mid-run** — `projectContext`, an observer shaped like (and wired next to) the existing `repeatGuard` in `loop.ts`, inspects every tool call's `cwd`/`path` argument, resolves the nearest `AGENTS.md` from there, and injects it (once per distinct project encountered in the run, deduped by resolved path — a long-running task that touches several repos gets each one's conventions exactly once) as a fresh user message right after that tool's result. The upward walk in both entry points **never leaves the home directory tree** (2026-08-28 owner correction, stage-4 review finding — the original text here said "home directory inclusive or the filesystem root, whichever comes first," which literally licensed climbing out of home for a `workingDirectory`/tool-call `cwd` with no ancestry in common with it, e.g. a path under `/tmp` — world-writable on macOS — reading whatever `AGENTS.md` any local process planted in a shared ancestor along the way, with no sandbox and, by default, no approval prompt to catch it): a `startDir` that resolves (via `realpath`, not a literal string compare — `/tmp`/`/var` are themselves symlinks on macOS) to somewhere outside the home directory returns nothing and triggers no walk at all; the home directory itself stays an **inclusive** stop, so an `AGENTS.md` placed directly at `~` is still found. Injection placement is deliberate and different from `INSTRUCTIONS.md`: this content varies by `workingDirectory`/discovered project, so per §5's prefix-stability rule it goes in the **final user message**, never the system message (`docs/model-context-inventory.md` §3.11) — the opposite of `INSTRUCTIONS.md`, which is stable across requests and stays in the system message. This is also explicitly flagged as an attack surface: a project's `AGENTS.md` is attacker-controlled the moment a user `git clone`s a hostile repository, and this agent has no sandbox and (§2.1) no approval prompt by default — so the rendered block always carries the source path (traceable in the step log) and an explicit precedence statement that the user's spoken task always wins and that project conventions can never authorise a destructive action the user didn't ask for or relax any safety rule.

Every mode's result is copied to the clipboard; auto-insert into the focused field is an additional delivery step, never a replacement for the clipboard copy. Only `transcribe` honors the `automaticallyInsert` setting — `ask` always stays in the voice surface + clipboard and never auto-inserts regardless of the toggle (so a spoken question can't paste a long answer into a chat box), and `agent` is draft-only. Auto-insert is additionally guarded by `OutputDeliveryPolicy.shouldInsert`, which downgrades to clipboard-only when the frontmost app changed since capture, and an opt-in `retainClipboardAfterInsert` setting can restore the user's prior clipboard after a successful insert. Since the 2026-08-15 batch's §J that same seam also consults a small built-in per-app table (`AppRules.swift`) — terminals never receive an auto-insert, since `ContextBridge.insert` is clipboard + ⌘V and a dictated newline in a shell is a command, and a handful of messaging/notes/editor apps supply a `TranscribeVariant` default *only* for a user who has never chosen one (`AppConfiguration.userSelectedTranscribeVariant` is what makes 「没选过」 representable). A rule may only restrict what was asked for: the focus guard runs first and a rule can never re-enable an insert it downgraded, no row may carry `autoInsert: true`. **There is no Settings switch for this** — `AppRules.transcribeVariant(for:userSelected:perAppRulesEnabled:)` and `OutputDeliveryPolicy.shouldInsert(...:perAppRulesEnabled:)` both take a `perAppRulesEnabled` parameter, but every call site (`AppModel.swift`) passes a literal `true`; the comment at each call site says this was a deliberate product decision — "no half-configured per-app behaviour," either real per-rule control exists or the table simply is how the product works — and the parameter is left as the seam a future per-rule control would be built on, not a live toggle. There is no PromptBuilder/EnglishOutputPolicy/LightTranscriptionPolicy layer anymore — those belonged to the old 5/6-mode Swift-native pipeline and were deleted along with it; mode-specific system prompts now live in the sidecar (`sidecar/src/oneshot/prompts.ts`, `sidecar/src/agent/loop.ts`), not in Swift, and are not user-editable (no Prompt Studio in the current design).

Key Swift-side collaborators `AppModel` wires together:

- `AudioRecorder` / `LiveSpeechTranscriber` — recording and on-device live-caption preview only (Apple's on-device recognizer, gated on the `liveCaptionsEnabled` setting); final recognition always goes through the sidecar's local MLX-Whisper, never this preview transcript.
- `GlobalHotKey` — configurable hotkey (hold left Option / double-tap Ctrl·Option·Shift / hold fn / etc.) that starts/stops a recording session; each recording locks in the active mode for that session.
- `ContextBridge` — Accessibility-based read of the current app's selection and write-back into the focused text field; clipboard is always the fallback delivery path.
- `SidecarClient` — spawns, health-checks, and now **supervises** the `sidecar/` child process (crash detection + auto-restart with status surfaced to the UI, added in the 2026-08-10 fix batch), then issues every request to it (`curl` over the Unix socket, not a native HTTP transport — still a known simplification, though the transport was hardened in that batch: request body via stdin instead of argv, concurrent pipe draining, per-request timeout, and cancellation, closing the old ARG_MAX/64KB-deadlock/no-timeout bugs — native-socket transport remains deferred). Also resolves `sidecar.env` if present in the packaged app's Resources, but that file is only bundled when `build-app.sh` is run with `--bundle-env` (off by default) — a distributed build has no bundled key and relies on the user-configured provider instead.
- `ImmutableAuditStore` — append-only local audit trail (`audit-events.v1.jsonl`) of `recognized`/`corrected`/`completed`/`cancelled`/`failed` events per request (`.corrected` is one-per-round in a Review-mode voice-correction session, chained via `supersedesEventId`); not affected by history reset or preference relearning. Raw audio itself is ephemeral and deleted after recognition. `provider`/`model` fields record fixed labels (`"mlx-whisper"`, `"deepseek"`/`deepseek-v4-flash`) as their zero-config default, but since the provider-config system below, a user who has explicitly configured a different Whisper/LLM provider will see that provider's own labels recorded here instead — this field reflects whichever backend actually served the request, not a hardcoded constant. The `.recognized` event additionally carries an **optional** `recordingEndedAt: Date?` (P2-12) — the instant the recording stopped, stamped in `AppModel.finishRecording()` — because `.recognized` is written *after* ASR returns and without it the trail cannot express the span the user actually waits through. Optional is what makes it migration-free on an append-only file: pre-2026-08-14 rows lack the key and decode as `nil`, and readers must **exclude** them from timing figures rather than count them as zero. `UsageStats` (`Sources/OpenType/UsageStats.swift`) is the pure aggregator over this file behind the History tab's local statistics panel — words dictated / average end-to-end wait / corrections per 100 words over a rolling 7 days, computed at read time, with no counters, no second store and no network path. Since 2026-08-25, `.completed` audit rows carry the effective `TranscribeVariant` that decided delivery, and the "average wait" figure excludes Review sessions from its timing spans — a Review commit made without a single correction was previously indistinguishable from a Direct delivery in the trail, so the user's own reading/editing time was silently counted as system latency; a pre-2026-08-25 row has no variant and keeps counting, since it can't be back-filled. The headline also splits into a transcribe figure and an ask figure (computed from the same filtered spans, so an all-dictation week shows the same number twice rather than two disagreeing ones) — dictation answers in ~2s, a web-searching `ask` can take 30s, and averaging them together read as "dictation got slower" whenever a user asked more questions that week.
- **Memory and history now run on two stores, not four**, converged by the 2026-08-25 unified-memory batch (`docs/superpowers/specs/2026-08-25-unified-memory-and-recent-context-design.md`): `ImmutableAuditStore` above (audit, unchanged) and the sidecar's `episodic_events` table (`sidecar/src/memory/`, alongside `entity_terms`/`owner_facts`/`conversations`), which is now the single source for both memory injection and the dictation history page. Deleted entirely, not just partly: `HistoryStore.swift` (a local `history.json` file the dictation page used to read), `AgentMemoryStore.swift` (a 660-line SQLite layer whose read side P1-7 had already deleted — by this batch its 8 `@Published` properties had zero subscribers left, UI included, so the write side and the SQLite table itself went too), `MemoryInsightsAnalyzer.swift` and `OwnerProfileAutoUpdater.swift` (only `AgentMemoryStore` called either), and `AppConfiguration.agentMemoryEnabled` plus Settings' "重置 Agent 记忆" button. Before this batch three sidecar routes each wrote their own episodic event from only the half of the truth they could see: `/asr/transcribe` didn't know the real mode or the frontmost app (so every `ask`/`agent` turn also logged a second row mislabeled `transcribe`), and `/oneshot/ask`/`/agent/run` hardcoded a placeholder `applicationName`; none of the three could see a Review-mode edit or a `tidy` rewrite, since both happen to the transcript after the sidecar has already answered. Now there is **one write point**: `EpisodicEventRecorder.swift` (pure body-builder) + `AppModel.recordEpisodicEvent(for:_:)` (best-effort `POST /memory/events`), called right beside the matching `.completed` `recordAuditEvent(...)` call, so mode/real app name/actually-delivered text are correct by construction because Swift is the only place that knows all of it at once, and only once delivery has actually completed. The write is gated by `EpisodicEventRecorder.shouldRecord(for:keepHistory:isPractice:)` (`status == .completed && keepHistory && !isPractice`) — `AppConfiguration.keepHistory` (Settings' 「保留本地输入历史」) is therefore the one lever that keeps a turn out of every future `ask`/`agent` request's context too, not just off the visible history list. `episodic_events` gained a nullable `conversationId` column; schema changes here reset rather than migrate (`applySchema`/`SCHEMA_VERSION` in `sidecar/src/memory/db.ts` drop-and-rebuild only this table on a version mismatch — `entity_terms`/`owner_facts`/`conversations`/`memory_consolidation_runs` are untouched, since those are stores the user can see and has edited). `MemoryStore.recentEvents(limit, { excludeModes })` is the by-time read query that never existed before this batch. It serves two consumers: the dictation history page (`GET /memory/events`, `DELETE /memory/events/:id`, `DELETE /memory/events`; `HistoryEntry.id` is now the row's `Int`, not a `UUID`), and `sidecar/src/memory/recentActivity.ts`'s `buildRecentActivityContext`, which renders the most recent `RECENT_ACTIVITY_LIMIT` (10) cross-mode turns — dictation included, no opt-out (`RECENT_ACTIVITY_EXCLUDED_MODES = []`, a deliberate 2026-08-25 product decision made after full knowledge of the cost, not a placeholder) — as one-JSON-object-per-line into the `ask`/`agent` user message (never the system prompt; see §5 of `docs/model-context-inventory.md`'s prefix-stability rule). Consolidation keeps its own, separate `transcribe` exclusion (`CONSOLIDATION_EXCLUDED_MODES`, `MemoryStore.consolidationCandidates()`, `startupConsolidation.ts`'s ≥12h/≥5-event gate) — that pass is a real model call producing durable memory (`entity_terms`/`owner_facts`), a different boundary from the ephemeral per-request injection, so the two stay two independent queries rather than one with a flag. Agent only (never Ask) additionally gets `opentype__read_history` (`sidecar/src/agent/readHistoryTool.ts`, registered in `coreTools.ts`, absent from Ask for free since Ask's toolset is built from its own allowlist) to expand a clipped `eventId`/`conversationId` from that block into its full untruncated record; its `limit` is clamped (falls back to 10, caps at 50) because SQLite reads a negative `LIMIT` as unbounded and this table now holds every dictation the user has ever spoken. The entity dictionary itself is unchanged by this batch — still editable via `POST/PUT/DELETE /memory/terms(/:id)`, still shows an `origin` badge, still has a reversible `POST /memory/consolidation-runs/:id/rollback`. Nothing Swift-side is injected into Agent-mode context directly: the `/agent/run` body is `task + context + conversationId + runId` (the field is `context`, not `selectedText`) — the recent-activity block reaches the model exclusively through the sidecar side.
- `Views.swift` / `SidebarShell.swift` / `SessionsViews.swift` / `DictationViews.swift` / `MemoryViews.swift` / `SettingsViews2.swift` / `McpServerViews.swift` / `MenuBarPopoverView.swift` — the UI. Still Alfred-style at the top level: the menubar `NSPopover` (`MenuBarPopoverView`) is the always-reachable surface — clicking the status-bar item only ever shows the popover, never the main window — but since the **2026-08-14 redesign** (`design_handoff_opentype_redesign_v1/`) it carries a row of three mode cells plus what is running and the two most recent sessions, because the main window is `.accessory` and usually closed, so the menu bar has to answer "how is the thing I just asked for going?" rather than only "which mode is next".
  The main window is now **a sidebar and one main thing**, not five equal bottom tabs. `AppTab` is four cases — `sessions` / `dictation` / `memory` / `settings` (`AppModel.swift`) — rendered by `SidebarShell` as sidebar 212 | list 334 | detail, collapsing below 720pt to a 52pt icon rail with the detail **pushed** over the list. `home` is gone (mode selection moved to the sidebar's mode card and the popover); the old Q&A and Agent tabs merged into one **会话** list (`SessionList.merged`, filtered by `SessionFilter`, a running task pinned on top as a whole card) — note this merged the *lists*, not the modes: a session's `SessionKind` still decides whether its next turn goes to `/oneshot/ask` or `/agent/run`. 记忆 was lifted out of Settings to a first-class page, and Settings' nine sections became five groups with provider/tool configuration pushed to sub-pages (`SettingsRoute`) — six since 2026-08-15, when 开机自启 opened a 「通用」 group above 快捷键. `DesignTokens.swift` (`DS.*`) is the closed scale — six type sizes, four radii, one accent — that replaced twelve font sizes and eight radii; **use it rather than literal values**. Opening the main window switches `NSApp.activationPolicy` to `.regular` (Dock icon, Cmd-Tab-able); closing it reverts to `.accessory`.

**Provider configuration (Whisper local/remote, LLM Anthropic/OpenAI-compatible) was reintroduced** after having been deliberately removed in the rewrite above — the product owner wants real, user-configurable providers back, on purpose, not by accident. This is *not* a return to the old per-platform `ProviderVault`/`AIServiceClient`/`AIProvider`/`CredentialProvider` Swift-side layer (that stays removed as dead code); the new system is sidecar-owned, consistent with the sidecar already owning all ASR/LLM logic:
  - **Whisper**: `local` (the existing sidecar-managed MLX-Whisper process, still the default) or `remote` (implements OpenAI's `POST /audio/transcriptions` shape against a user-supplied base URL + API key, so a self-hosted OpenAI-API-compatible transcription server works too, not just `api.openai.com`). `sidecar/src/asr/remoteWhisperClient.ts` is the remote client; `server.ts`'s `resolveTranscribe` picks local vs. remote per request based on the saved config, so `/asr/transcribe`'s request/response contract is identical either way.
  - **LLM provider**: either Anthropic (Messages API, `/v1/messages`) or OpenAI-compatible (Chat Completions, `/chat/completions` — DeepSeek/OpenAI/many self-hosted servers) — `sidecar/src/provider/anthropic.ts` and `sidecar/src/provider/openaiCompatible.ts`, dispatched via `sidecar/src/provider/registry.ts`. Both implement `chat`/`testConnection`/`listModels`; `server.ts`'s `resolveChat` uses the saved config if one exists, otherwise falls back to the original always-available env-based DeepSeek client (`provider/deepseek.ts`, untouched) — so a zero-config dev checkout still works exactly as before.
  - **Config storage/API**: the sidecar persists both configs as plaintext JSON (`ProviderConfigStore`, `sidecar/src/provider/configStore.ts`) next to its existing SQLite data directory, `chmod 600`'d — a deliberate tradeoff (not Keychain) documented in that file's doc comment: the sidecar already stores other locally-sensitive data unencrypted (the memory SQLite DB), and Keychain-on-Swift-side would reintroduce exactly the credential-plumbing-through-env-vars-at-spawn-time coupling this rewrite removed. `sidecar/src/provider/routes.ts` exposes it over HTTP (`GET/PUT /config/llm`, `GET/PUT /config/whisper`, `POST /config/llm/test`, `POST /config/llm/models`, `POST /config/whisper/test`, `GET /config/status`) — Swift never talks to Keychain or writes provider config itself, it just calls these endpoints (`AppModel.swift`'s "Provider configuration" section) the same way it calls every other sidecar endpoint.
  - **"Configured" is explicit, not ambient**: `providerConfigStore.getStatus()`'s `llmConfigured`/`whisperConfigured` flags are only set by an actual `PUT /config/llm`/`PUT /config/whisper` call (i.e. the user finished Test Connection + model pick + Save, or explicitly chose local Whisper) — an ambient `DEEPSEEK_API_KEY` env var alone never flips them. This is what `GET /config/status`'s `ready` field (and Swift's `AppModel.needsProviderOnboarding`) gates the first-run setup wizard on.
  - **Onboarding wizard**: `Sources/OpenType/ProviderSetupViews.swift`'s `OnboardingWizardView` takes over the main window's tab content (`RootView` in `Views.swift`) in place of Home whenever `needsProviderOnboarding` is true, and the app auto-opens that window the first time launch discovers this (`AppModel.init`'s post-sidecar-ready check). It reuses the exact same `WhisperSetupContent`/`LLMProviderSetupContent` views Settings' "语音识别"/"AI 模型" sections embed — one implementation of configure/test/list/save, not a parallel wizard-only copy.
